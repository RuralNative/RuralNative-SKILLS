## Shared handoff contract

Planning owns validated parent/ticket bodies, stable criterion IDs, and canonical authoritative sections. Implementation computes the requirements pin from those bodies, gathers proof, and owns the PR body. Review consumes that proof and publishes findings; it does not repair the PR body.

Keep one authored requirements/evidence contract in the existing shared-code generation mechanism, packaged into each independently installable skill. Do not require sibling skill installations or import files outside an installed skill. Share parsers and validators, not a new workflow service. Distinguish `missing`, `malformed`, `unsupported-version`, `stale`, and `current` evidence. A missing pin is never equivalent to an empty matching pin.

The common handoff validator covers ticket/parent identity, criterion coverage and passing proof, requirements revision, and evidence-to-head association. Implementation uses it before publishing and on the read-back PR; review derives readiness from it. Review-specific checks, including local checkout match, standards, and CI, remain separate. A handoff validation failure prevents implementation from reporting successful delivery or instructing the user to begin review.

## Implementation steps

   Preserve explicit human invocation as authority for the single ticket's implementation and normal PR delivery, subject to host approvals. Do not add an unconditional second approval question for creating the promised PR. Permission denial remains a precise stop, never a bypass.

2. **Separate initial eligibility from delivery repair.** Capture read-only issue, parent, dependency, branch, and existing-PR facts before deciding the path. Initial work retains ordinary `ready-for-agent` validation. The exception for `ready-for-human` requires exactly one verified matching open PR in the same repository, correct ticket association, base `main`, and matching current feature branch. Zero or multiple matches, a wrong branch/base/repository, changed requirements, blockers, needs-info, or an assignee remain stops. Keep the unassigned-ticket rule; expanding ownership/resume rules is out of scope. Read the prior evidence revision before repair rather than repinning changed requirements as if the old evidence were fresh. No automatic reset, stash, checkout switching, or force push.

   On a clean ticket branch with committed work but no PR, ordinary ready-for-agent eligibility permits continuing delivery only with available, validated evidence for that commit. Do not redo completed code or make an empty commit. After loss of the original pin or bug RED evidence, stop with an evidence-recovery diagnostic; adding durable checkpoints or reconstructing missing historical proof is out of scope. A dirty interrupted checkout still requires user cleanup. When invoked from main and the ticket branch already exists, identify it and stop with the switch instruction instead of blindly recreating it.

3. **Specify and test an ordered delivery procedure.** Use existing pure helpers with captured facts; add only small missing decisions/body composition helpers, not a new orchestration service.
   - Validate criterion evidence locally and render the body without publishing.
   - Inspect the intended diff and commit only ticket changes on the validated feature branch, respecting host approvals. Reuse an existing implementation commit when appropriate.
   - Re-read requirements and gate before publication. Push the feature branch to the explicit remote and verify its head equals the intended local commit. Never push to `main`.
   - Re-query matching PRs. Create one when absent; update the one matching PR when present; stop on ambiguity. Recheck requirements immediately before the body write.
   - Compose `Closes #<ticket>` and exactly one compact evidence block in the same PR-body operation, preserving unrelated body content. Do not use evidence comments.
   - Bind new evidence to the final committed head SHA in the PR-body envelope, outside the commit to avoid a circular hash. Rerun affected checks if implementation changes after verification. Do not treat a matching requirements pin alone as proof for a different code revision. Recognize an existing semantically valid target closing reference; do not rewrite unrelated closing references. Conflicting ticket associations stop instead of guessing.
   - Read back the PR and verify repository, open state, base, head branch and SHA, valid closing reference, evidence content/revision, and current issue-body revision. Feed observed facts into the completion decision rather than assuming success from a write response.
   - Only after verified PR publication perform the existing ready-for-human transition. If bookkeeping fails, report the verified PR URL and the remaining operation distinctly; do not recreate the PR on resume.
   - On a timeout or uncertain create/update result, re-read GitHub before retrying. On push/auth/permission failures, report the failed operation and preserve local work. On missing evidence or changed requirements, stop rather than inventing successful evidence. GitHub writes are not transactional; a post-write freshness mismatch must be reported as stale, not successful delivery.

## Acceptance criteria

- AC-1: The installed command no longer depends on or invokes `/implement` or mandatory `/code-review`; focused implementation proceeds directly to PR delivery, with explicit review handoff only afterward.
- AC-2: Fresh eligible work produces one PR against `main` whose head equals the pushed implementation commit and whose body contains the correct closing reference and one valid evidence block.
- AC-3: A requirements mismatch observed before publication causes zero PR create/update calls. A mismatch detected after a write prevents a success report.
- AC-4: Repeating delivery on one matching PR with `ready-for-human` repairs or confirms it without duplicating the PR or redoing completed implementation. The prior evidence revision remains the authority for reuse.
- AC-5: Needs-info, blockers, assignees, dirty or mismatched checkouts, invalid PR identity, and multiple matching PRs stop with specific diagnostics and no unsafe writes. Fresh tickets without `ready-for-agent` still stop.
- AC-6: Commit, push, PR-write, and bookkeeping failures identify the exact incomplete step. An ambiguous network result triggers read-back before retry, and an existing verified PR is preserved.
- AC-7: LF and CRLF evidence bodies are readable; repeated body composition preserves unrelated prose and yields one closing reference for the target and one evidence block.
- AC-8: Documentation describes the self-contained command, the approved invariant changes, and current review-only ownership. Generated workflow-state copies match their authored source.
- AC-9: Canonical planning output passes through requirements parsing, implementation evidence creation, PR-body read-back, and review readiness without hand-editing. Unrecognized or ambiguous requirement syntax produces a diagnostic before pinning/publication, not an apparently valid hash of missing requirements.
- AC-10: A newly created PR missing a pin, carrying a malformed/stale pin, incomplete proof, or proof for another head cannot pass either implementation completion or review readiness. Valid matching output passes both. Missing pins cannot exploit the legacy exception without affirmative provenance.
- AC-11: REVIEW.md absence causes no file write and no missing-policy stop. Existing project rules still apply. Changes to effective governing rules or configuration invalidate reused review verdicts, with and without that file.
- AC-12: Fresh completion, committed-but-unpublished continuation, and matching-PR repair have distinct tested paths. Missing historical proof produces an honest recovery stop; no test or prose claims that such proof is reconstructed automatically.
