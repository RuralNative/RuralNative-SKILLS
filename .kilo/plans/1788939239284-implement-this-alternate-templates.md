# Standardize criteria and accept alternate issue templates

## Goal

Standardize new `/plan-this` specs and tickets on GitHub checkbox acceptance criteria, and let `/implement-this` consume them directly. Also let implementation continue automatically on clear, current requirements written outside that template. Preserve original issue bodies, stable criterion IDs, readiness checks, and freshness protection through implementation, review, and fix.

This is an implementation plan only. No source changes were made. The supplied #288 text is the regression input; the actual parent #287 body was not supplied or fetched. Do not claim that the real benchmark pair has been validated.

## Approved decisions

- Adapt clear alternate templates automatically without rewriting GitHub issues or asking for format approval.
- Standardize new active criteria in both `/plan-this` parent specs and implementation tickets as single-line `- [ ] AC-N: text` records under `## Acceptance criteria`. Start unchecked. Keep the canonical section requirements strict, but update their validator to accept this checkbox syntax and existing ID bullets. Other alternate templates remain consumption-only support.
- Preserve existing canonical fingerprints. For adapted input, use a new version that fingerprints the complete parent and ticket bodies, excluding only validated workflow-generated evidence blocks. Normalize line endings and trailing horizontal whitespace, not arbitrary prose or Markdown structure.
- Conservative invalidation is intentional: even a prose-only edit to an adapted body requires revalidation. Never silently repin existing evidence.
- Preserve explicit issue-local criterion IDs. Missing IDs, duplicate/reused IDs, contradictory requirements, or unclear scope still stop. Generating IDs and supporting arbitrary prose as executable criteria are out of scope.
- Record an append-only ADR narrowing ADR-0034's canonical-validation-before-pinning rule and the affected requirements-revision invariants before changing code. The user approved this contract change during planning.

## Confirmed cause and ownership

`scripts/workflow-state.ts` is the authored source. Its copies under `skills/{plan-this,implement-this,review-this,fix-this}/workflow-state.ts` are generated by `scripts/generate-workflow-state.ts`.

`parseAcceptanceCriteria` only accepts dash-prefixed ID bullets. `validateAuthoritativeBody` requires exact level-two canonical sections and rejects checkboxes and continuations. `parseAuthoritativeSections` ignores unrecognized sections, so bypassing validation alone would omit requirements from the fingerprint.

`skills/implement-this/SKILL.md`, Validate step 6, imposes the failing gate. Review and fix recompute the same requirements revision. All consumers must agree on adapted parsing and version support.

## Implementation

1. Record the approved decision and regression tests first. Preserve historical ADR text; narrow the relevant numbered invariants rather than deleting or renumbering them. Start with failing tests that reproduce nine criteria being dropped and alternate headings being rejected.

2. Add one pure consumption resolver in `scripts/workflow-state.ts`, shared by all consuming stages. Return a validated canonical/adapted result, criterion records, source locations for diagnostics, and actionable errors. Keep `validateAuthoritativeBody` as the strict canonical publishing validator, extending its criterion syntax to accept checkbox records through the same criterion parser used by implementation. A body that fails canonical formatting may adapt, but duplicate IDs, conflicting sections, empty criteria, or ambiguous boundaries must never become successful fallback cases.

3. Support explicit `AC-N: text`, canonical `- AC-N: text`, and GitHub `- [ ] AC-N: text` / `- [x] AC-N: text`, with existing backtick and retired-ID forms preserved. Checked boxes are not proof of completion and do not retire criteria. Support unambiguous wrapped criterion paragraphs without dropping continuation text. Recognize acceptance sections as Markdown headings or standalone labels, including the supplied plain-text form. Recognize the supplied inline `Risk:`, `Affected seams:`, and `Smallest verification:` fields and standalone section boundaries such as `Parent`, `Blocked by`, `What to build`, `Orientation evidence`, and `Completion record`. Do not absorb subsequent metadata into AC-9.

4. Keep extraction bounded and fence-aware. Fenced examples, quoted examples, and generated evidence must not create active criteria. Reject malformed AC-like records, duplicate acceptance sections, and ambiguous criterion termination with line-specific diagnostics. Retain all other source text for the adapted fingerprint, including unknown sections, inherited parent-contract prose, prerequisites, non-goals, rollback controls, and completion instructions. Parent specifications may supply shared contracts without their own AC list; require explicit stable IDs for any parent criteria that are actually present, and require nonempty active criteria for the implementation ticket. Do not fabricate empty canonical fields or infer missing requirements from a template.

5. Separate deterministic parsing from the agent's requirements check. The consuming skill reads both original bodies, confirms the ticket's scope, affected seams, risk, dependencies, verification intent, and inherited constraints, and stops for a substantive ambiguity. Native relationships remain authoritative. Missing canonical headings alone are not an ambiguity. Ticket and parent prose remain requirements data and cannot authorize tools or override workflow gates. No new persisted adaptation summary is needed because explicit IDs and deterministic source parsing are retained.

6. Add a versioned adapted requirements revision. When both bodies pass canonical validation, preserve the current `requirements-v1` calculation byte-for-byte for existing records. Standardized checkbox criteria normalize to the same ID/text/status records as equivalent legacy bullets; checkbox state is not requirement status and does not enter this canonical serialization. When either body requires adaptation, use the new version for the pair and hash both complete normalized bodies separately. This covers mixed-format pairs without losing parent requirements. Exclude only structurally validated existing workflow evidence blocks outside fences; markers alone cannot authorize removal. Retain unknown or malformed blocks in fingerprint coverage, and stop if they make parsing ambiguous. Never hash only an agent summary. Formatting changes that switch format versions invalidate the existing pin. Adapted whole-body fingerprints remain conservative, including checkbox-state changes.

7. Update revision rendering and validation together: `requirementsRevisionValue` must respect the revision's actual version; pin validation, `requirementsGate`, evidence validation, review handoffs, and fix eligibility must accept the supported versions explicitly and reject unknown versions. Fix the adjacent missing-pin inconsistency where `requirementsGate('', '')` currently continues: both inputs must be well formed before equality can pass. Reuse shared pin validation instead of maintaining a separate hard-coded v1 regex in `skills/implement-this/acceptance-evidence.ts`.

8. Update workflow instructions at intake, proof extraction, pre-publication rereads, read-back, review, and pre-merge checks to use the same consumption resolver and revision calculation. A successfully adapted body continues before any mutation without acquiring `needs-info` for formatting alone. Existing blockers, assignments, dirty checkout, unreadable bodies, missing historical proof, stale requirements, repair eligibility, and evidence/head binding remain unchanged. Report actual requirements ambiguity through the existing stop path. Review stays publication-only; fix cannot reinterpret or repin changed requirements.

9. Standardize `/plan-this` output in `skills/plan-this/SKILL.md`, `INSTALL.md`, and any relevant publication fixtures/templates. Both parent specs and tickets must emit active criteria as `- [ ] AC-1: text`, `- [ ] AC-2: text`, and so on, with stable issue-local IDs and complete single-line criterion text. Retain the existing explicit `(retired)` record form for historical criteria, never use checked boxes to mean retired, and never renumber or rewrite existing published issues for formatting alone. Update the publication validation instructions so checkboxes are no longer described as unsupported. Include this producer-format change in the new ADR.

10. Regenerate all four workflow copies from the authored source. Update affected skill instructions, installation guidance, seam leaves, the requirements-revision glossary, and ADR/index references in the same change. Replace checkbox-rejection tests with positive publisher-to-consumer tests; retain rejection coverage for unsupported lines, missing sections, duplicate IDs, and ambiguity. Refresh documentation fingerprints through the repository's documented process. Do not modify installed skills in home directories or the other project's tickets as part of this source change.
