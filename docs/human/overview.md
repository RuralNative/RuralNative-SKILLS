This repository publishes reusable skills for coding agents. The shelf includes documentation workflows, prose cleanup that stays active over agent output once loaded, planning, implementation, code review, and release work.

The documentation skills treat the doc tree as a cache for what code cannot recover. `document-for-agents` runs the lifecycle — establish, audit, improve, maintain. The cache's tier grows itself: a repository starts minimal (just an index, glossary, and conventions) and promotes to standard and then full as real needs appear — a durable decision, more than one independently editable seam, or multi-agent coordination — in the same run that notices them, and never shrinks automatically. Destructive changes (trims, moves, deletions, demotion) still need one explicit Improve approval. Orientation is bounded at runtime: each task resolves its own small set of documents — the compact index, the affected seam's leaf, the glossary entries it names, and only the decisions and policies its leaf explicitly declares required — and that set counts once in UTF-8 bytes under a strict cap (6,000 ordinary, 9,000 API or route, 12,000 schema or data, 7,000 re-orientation, 12,000 absolute). Compact citations stay visible navigation and never load; duplicate sources count once; rejected decisions never enter the set and superseded decisions stay out of current guidance unless declared required; and the exhaustive inventory lives in a harness-owned manifest that never joins any read set. Unrelated documentation growth can never raise one task's cost. An older bloated cache is not silently claimed compliant: the Improve path shows one complete migration preview, waits for explicit approval, and only then applies the approved trims, moves, deletions, manifest changes, and generated-doc actions before the prose audit and harness pass. Every lifecycle run first settles three gates: the tier it needs, the private diagnostics consent, and whether any decision is still missing its rationale. Decisions now record their context, alternatives, and rejection reasons before the code work starts, so the reasoning survives. Each documented seam carries a code fingerprint that fails the doc check when the docs drift from the code — in a working tree and in clean CI alike — and refreshing it only after the affected claims are reviewed against the code.

`plan-this` defines an intent capsule (`Outcome`, `User`, `Why now`, `Success`, `Constraints`, `Non-goals`) from the task, conversation, code, and documentation, optionally explores three directions when the solution form is unsettled, then asks only the choices a human must decide — when repository facts and the confirmed task cannot decide a choice that changes product behavior, scope, cost, risk, or an action that is hard to undo — one plain question at a time, using repository-owned `unslopify` and the focused agent cache `AGENTS.md -> ARCHITECTURE.md -> seam leaf -> CONTEXT.md`. A complete settled capsule reaches the preview without a forced question; the preview explains what will be created, the main risks, and what happens next, and publication waits for explicit approval. Planning forms the fewest coherent tickets first: support work stays with its behavior, a small task ships as one complete ticket, and splits happen only at real boundaries that the approval preview states for each ticket. Parallel execution follows natural ticket boundaries rather than creating them — independent tickets start together, real blockers become native edges, and file overlap without semantic dependency becomes a scheduling collision. `implement-this` validates one ticket, several ready tickets, or a parent specification against the frontier, allows one parentless standalone ticket but rejects parentless multi-ticket sets, then automatically dispatches every ticket — including a single-ticket run — through an isolated worktree and worker session created with Kilo's `agent_manager` tool in worktree mode without waiting to be forced; the first worker-management call is the Agent Manager overview (`action: "list"`) and the tracked `agent_manager: allow` and `task: ask` project permission gate ensures dispatch is automatic while Task runs only after explicit approval (never edits `.kilo/agent-manager.json`); status comes from the Agent Manager overview and completed workers use the supported stop control; the command session reserves tickets, watches progress, and reports; workers run a single `/implement` stage under the same prose and cache rules; the command never edits ticket code itself, does not substitute Task for the worktree, and stops before any claim if Agent Manager is unavailable, and it does not host code review. `review-this <target>` owns one pull-request review wave for its parent specification. The target can be the parent specification, a child issue, a pull request, or a full URL, and bare numbers (`100`) and hash numbers (`#100`) mean the same thing. It resolves the target to its exact GitHub objects and pull-request set before any worktree is created or anything is written, then discovers native child tickets, linked pull requests, blockers, checks, reviews, and current head and base SHAs, automatically creates one persistent PR worktree and worker per ready pull request via `agent_manager` in worktree mode after the Agent Manager overview before any Standards, Spec, or fix `Task` subagents (Task never replaces those worktrees and nested Task contexts run only inside them after explicit approval), reviews ready pull requests concurrently within three review workers per stage and four managed workers across the workspace while each active pull request proceeds independently, starts cloud collection together with the local review so neither waits for the other, gives both fresh review axes one shared revision packet per pinned revision pair plus their axis-specific brief, reconciles Kilo cloud review with the local Standards and Spec review, routes confirmed findings, squash-merges clean heads, promotes newly unblocked dependents, and closes the specification when final verification and whole-spec review pass. #155 ships the implementation behavior and #156 ships target resolution; #157 and #158 remain pending. Every ticket delivers by pull request.

Child-issue and parent-wave selection requires each pull request to be linked to the same ticket it closes and to carry non-empty current head and base revisions.

Direct pull-request review also withholds auto-merge authority when the linked ticket and closing reference disagree.

The installed skill metadata uses the same `/review-this <target>` invocation as the body and installation guide.

The document seam records the attention boundary as separate invariants. It also keeps an optional, private log of confirmed agent mistakes: the skill asks once, at a checkpoint you cannot skip, whether you want the log at all, and remembers your answer in a private file outside version control; nothing is written unless you consent, every update announces itself first, the file never enters agent read sets or version control, and nothing uploads without your review (ADR-0018, ADR-0028).

One written file governs every review. `REVIEW.md` at the repository root says what reviewers check, how findings are graded, and that review subagents only read while the main reviewer verifies each finding. Cloud review reads the same file from the pull-request base branch; setting up that cloud service is separate configuration work outside this repository.

The model you choose for the review command session stays the reviewer and manager. It owns the shared revision packet, checks that Standards and Spec are complete, verifies every candidate finding, reconciles them across axes, publishes the verdict, and alone merges, labels, promotes, and closes. At the start of each `/review-this` run it asks once for a cheaper execution model from the live Agent Manager catalog (model, optional provider, optional variant, no hardcoded names) and applies that choice to every new fix worker in the wave. A resume shows the earlier choice but you confirm it before any new worker starts. The fix worker may edit, repair, and fast-forward push only inside its own persistent worktree; it cannot publish a verdict or change merge, label, promotion, closure, or parent state. One corrected fix packet is allowed inside the existing fix budget; continued failure stops the ticket with `needs-info` and never silently hands the work back to the frontier model. Required Standards category statuses travel through the review adapter and are checked before reconciliation; a finding missing a category or severity is rejected, never invented as a blocking correctness finding. Standards and Spec stay separate even at the same code location, and cloud and local findings collapse only when the revisions and evidence identify one defect. Test strategy, accessibility, observability, migration, and simplification run as triggered checks inside Standards, not new review axes, and at most one specialist supplements a full-review round: security for the strongest trust-boundary risk, or web performance for measured web-performance work.

The three workflow skills agree on state because they share one decision module. It looks at GitHub facts and worker and pull-request facts, then returns the next safe actions: what is ready, how many workers may run, when to retry, whether a review is current, and when work may merge or a specification may close. Labels follow the blockers. Every installed skill carries the same copy of this module.

The workflow commands now consume the bounded orientation contract directly: `plan-this` resolves an orientation set for each proposed ticket before publication approval and rejects an over-budget ticket, `implement-this` resolves current sources in the worker checkout before broad documentation loading and gives a direct ticket with valid affected seams the same bounded path, and `review-this` resolves orientation sources once per pinned head-and-base pair and shares the compact evidence across Standards and Spec. The compact evidence stays small — task band, resolved bytes, cap, source count, cache-gap state — and exact source lists appear only on failure or approved substitution; an over-budget review set stops before broad loading and reports its exact sources.

A ticket starts only when its native GitHub blockers are closed. Every ticket delivers by pull request against `main`: the worker pushes its feature branch, opens one pull request with `Closes #<ticket>`, posts acceptance evidence, and the squash-merge closes it. No path pushes directly to `main`.

Accepted criteria keep one stable identity across planning, implementation, and review. `plan-this` publishes each criterion with a local ID unique within its own issue, written `AC-1`; the stable criterion key is the authority issue number plus that local ID, so two issues may both use `AC-1`. Clearer wording keeps the same ID, changed observable behavior gets a new ID and retires the old, and retired IDs are never reused or accepted as active evidence. `implement-this` dispatches criteria as records (ID, text, and active or retired status) and workers cite and prove evidence by ID rather than by full sentence text. Review keeps the same key: Spec findings and whole-spec verification name `#<issue>:AC-N`, never prose.

The three skills form the complete workflow. `plan-this` publishes the parent specification and native child tickets; `implement-this` runs up to three isolated pull-request workers per stage; `review-this <target>` reconciles Kilo cloud comments with the local Standards and Spec review before merge, promotion, and closure. GitHub keeps enough state to resume from the parent specification after any pause.

The accepted command-session design starts implementation and review independently whenever each stage has work. Each session manages its own workers, finishes its own frontier, and reports cleanup honestly: `needs-info` worktrees stay for diagnosis even on a closing host; worktrees close only through supported Kilo actions, and when chat cannot close one the run says `cleanup-pending` instead of deleting anything. There is no supervisor or coordinator. ADR-0019 records these rules. #155 implements the implementation side, #156 ships target resolution, and #157-#158 add risk classes, measured lifecycle phases, setup reconciliation, one persistent initial-review worktree, fresh fix contexts, and delta/full rereview.

### Workers stay live until delivery is durable (ADR-0023)

A worker never stops itself, and only the command session may clean up. Stopping and removing are separate decisions: unfinished, interrupted, failed, dirty, unpushed, or `needs-info` workers keep their session and worktree (`preserved-for-resume` or `preserved-for-diagnosis`). Cleanup happens only after exact source recovery — terminal success, a clean worktree, and one matching local/remote/PR head SHA — plus durable pull-request evidence. A merged review PR counts only when the three head SHAs were recorded before the squash-merge, because GitHub may delete the feature branch at merge. When a worktree exists but its session is missing, the run reports `recovery-required` with the observed path and branch and never creates a duplicate or deletes it. ADR-0023 narrows the ADR-0019 cleanup rule.

### Performance contract shipped in #157

Planning now records `ordinary` or `high-risk` before publication. A high-risk trigger with evidence missing is an internal incomplete result that stops publication and risk labeling until the evidence lands. Ordinary tickets target 60 minutes from reservation to terminal outcome; high-risk tickets target 90 minutes. Implementation measures setup and lifecycle phases, reconciles dependency manifests after checkout and runs dependency setup only when the recorded state is missing or changed (unchanged state reuses the worktree setup), and carries a compact dispatch packet.

Review starts when a pull request has current head and base revisions plus implementation evidence. One persistent PR worktree remains through initial review, fresh fix contexts, delta rereviews, and final verification, with at most two code-fix rounds per pull request. Safe advisories join blocking fixes, advisory-only findings are deferred, and final-verification repairs receive a bounded rereview. SLO misses remain visible without relaxing safety gates. Before review publication and before merge the current issue bodies are hashed over their authoritative sections and compared with the requirements revision the delivery evidence pinned; a changed body stops the ticket with `needs-info` until it is reconciled and the run resumes.

### Worker evidence contract shipped with ADR-0021

Each `implement-this` worker now proves every active acceptance criterion by its stable local ID: behavioral criteria show a focused RED and GREEN, non-behavior criteria use one of four exemptions (`docs-only`, `static-content`, `rename-only`, `format-only`), dependency or configuration criteria named from the diff are never exempt, bug fixes supply worker-confirmed defect reproduction for the first behavioral RED, and version-sensitive or public-interface changes include worker-confirmed source and compatibility evidence in one stable escaped Markdown block.

### Frontier review authority shipped with ADR-0022

Issue #173 keeps the review trust boundary with the frontier command session: it owns revision packets, completeness, finding verification, reconciliation, verdict publication, merge, labels, promotion, and closure. One execution model from the live Agent Manager catalog is chosen once per invocation and applied to every new fix worker in the wave; the worker mutates only inside its persistent PR worktree and cannot publish verdicts or change tracker state. The adapter now transports required Standards category statuses, missing category or severity never becomes a blocking correctness finding, deduplication preserves axis identity, and at most one specialist supplements a full-review round. Issue #170 stays open until this ticket publishes preservation evidence for bounded wave fan-out, shared revision packets, cloud/local overlap, independent pull-request progress, and timing records.
### Triggered quality proof shipped with #172

When a diff exposes a conditional quality obligation, the worker adds exactly its narrow evidence section: browser behavior (asserted interaction plus console, network, accessibility, trace, or DOM runtime state from an existing repository or host browser capability; a generic screenshot is insufficient and no skill or unpinned browser tool is installed), security boundaries (assets, trust boundaries, abuse cases, focused control tests), production operability (on-call questions, bounded metric labels, whether the telemetry path was exercised), migrations (consumers, additive and destructive phases, cutover, rollback, boundary verification), and explicit performance (matched baseline and result conditions, variance, attribution, keep-or-revert). Planning keeps its existing fields and adds no quality-profile checklist. Unexpected failures follow a bounded reproduce, isolate, one-hypothesis, smallest-fix, regression-proof loop. The comparison source is pinned to the Addy Osmani `agent-skills` revision `f63ec56a3cc936408d792956ae583c3c96a825bd`, recorded with adopt, adapt, reject, and reference-only dispositions in `reference/vendor-facts.md`; no Addy source is a runtime dependency.

### Accepted command-session example

A specification has five tickets: #101 and #102 have no blockers, #103 is blocked by #101, #104 is blocked by #101 and #102, and #105 is blocked by #103.

1. Plan grills the open decision frontier, gets publication approval, and publishes the parent #100 and five children. #101 and #102 get `ready-for-agent`; #103-#105 get `blocked`.
2. Start an implementation command session with `/implement-this #100`. It selects the frontier #101 and #102, at most three, and dispatches each to its own worktree and pull request.
3. Start a review command session with `/review-this #100` independently when those pull requests exist. It discovers them, reconciles cloud and local findings against each current head, and merges eligible pull requests. When #101 closes, it promotes #103 to `unblocked` + `ready-for-agent`; when #101 and #102 close, it also promotes #104.
4. The implementation session manages its own frontier and can reserve #103 and #104 after promotion. The review session manages its own review frontier and handles those pull requests without a required per-wave handoff.
5. When #105 merges, the review session runs `npm run verify` on updated `main` and performs a whole-spec Standards and Spec review. A cross-ticket defect becomes the smallest follow-up child ticket; otherwise the parent #100 closes.

The implementation steps describe shipped ADR-0019 behavior from #155, target resolution describes shipped behavior from #156, and review fixes and delta rereviews now stay in the persistent PR worktree from #157-#158.
