This repository publishes reusable skills for coding agents. The shelf includes documentation workflows, prose cleanup that stays active over agent output once loaded, planning, implementation, code review, and release work.

The documentation skills treat the doc tree as a cache for what code cannot recover. `document-for-agents` runs the lifecycle — establish, audit, improve, maintain. The cache's tier grows itself: a repository starts minimal (just an index, glossary, and conventions) and promotes to standard and then full as real needs appear — a durable decision, more than one independently editable seam, or multi-agent coordination — in the same run that notices them, and never shrinks automatically. Destructive changes (trims, moves, deletions, demotion) still need one explicit Improve approval. Orientation is bounded at runtime: each task resolves its own small set of documents — the compact index, the affected seam's leaf, the glossary entries it names, and only the decisions and policies its leaf explicitly declares required — and that set counts once in UTF-8 bytes under a strict cap (9,000 ordinary, 13,500 API or route, 18,000 schema or data, 10,500 re-orientation, 18,000 absolute; ceilings are caps, not targets). Compact citations stay visible navigation and never load; duplicate sources count once; rejected decisions never enter the set and superseded decisions stay out of current guidance unless declared required; and the exhaustive inventory lives in a harness-owned manifest that never joins any read set. Unrelated documentation growth can never raise one task's cost. An older bloated cache is not silently claimed compliant: the Improve path shows one complete migration preview, waits for explicit approval, and only then applies the approved trims, moves, deletions, manifest changes, and generated-doc actions before the prose audit and harness pass. Every lifecycle run first settles three gates: the tier it needs, the private diagnostics consent, and whether any decision is still missing its rationale. Decisions now record their context, alternatives, and rejection reasons before the code work starts, so the reasoning survives. Each documented seam carries a code fingerprint that fails the doc check when the docs drift from the code — in a working tree and in clean CI alike — and refreshing it only after the affected claims are reviewed against the code.

`plan-this` defines an intent capsule (`Outcome`, `User`, `Why now`, `Success`, `Constraints`, `Non-goals`) from the task, conversation, code, and documentation, optionally explores three directions when the solution form is unsettled, then asks only the choices a human must decide — when repository facts and the confirmed task cannot decide a choice that changes product behavior, scope, cost, risk, or an action that is hard to undo — one plain question at a time, using repository-owned `unslopify` and the focused agent cache `AGENTS.md -> ARCHITECTURE.md -> seam leaf -> CONTEXT.md`. A complete settled capsule reaches the preview without a forced question; the preview explains what will be created, the main risks, and what happens next, and publication waits for explicit approval. Planning forms the fewest coherent tickets first: support work stays with its behavior, a small task ships as one complete ticket, and splits happen only at real boundaries that the approval preview states for each ticket. Parallel execution follows natural ticket boundaries rather than creating them — independent tickets start together, real blockers become native edges, and file overlap without semantic dependency becomes a scheduling note for user-managed parallel checkouts. `implement-this` validates exactly one open ticket and stops before mutation on multiple references, parent specifications, or pull requests, then implements it in the current checkout with no worktree, worker, or Agent Manager involvement; the tracked `task: ask` permission posture governs the optional fix round (never edits `.kilo/agent-manager.json`); there is no worker status to poll and no stop control to use; the run validates one ticket and runs a single `/implement` stage under the same prose and cache rules; the run stops before any write on validation failure, and it does not host code review. `review-this <target>` owns one pull-request review in the current checkout. The target can be the parent specification, a child issue, a pull request, or a full URL, and bare numbers (`100`) and hash numbers (`#100`) mean the same thing. It resolves the target to exactly one open pull request before anything is written, then reads the linked ticket, blockers, checks, reviews, and current head and base SHAs, runs one frontier Standards-plus-Spec pass in the current checkout with no worktree, worker, or Agent Manager involvement, reviews the single pull request with one frontier pass, publishes the verdict, squash-merges the clean head, promotes newly unblocked dependents, and closes the parent only when every child is closed with no post-merge verification and no whole-spec review. Every ticket delivers by pull request.

Single-target resolution requires the pull request to be open, linked to the ticket it closes, and pinned to current head and base revisions matching the checkout.

Direct pull-request review also withholds auto-merge authority when the linked ticket and closing reference disagree.

The installed skill metadata uses the same `/review-this <target>` invocation as the body and installation guide.

The document seam records the attention boundary as separate invariants. It also keeps an optional, private log of confirmed agent mistakes: the skill asks once, at a checkpoint you cannot skip, whether you want the log at all, and remembers your answer in a private file outside version control; nothing is written unless you consent, every update announces itself first, the file never enters agent read sets or version control, and nothing uploads without your review (ADR-0018, ADR-0028).

One written file governs every review. `REVIEW.md` at the repository root says what the frontier reviewer checks, how findings are graded, and which structured evidence makes a finding valid. There is no cloud review or review subagent. The optional `review-fixer` edits and runs approval-required focused tests only; the frontier reviewer verifies its diff and keeps all commit, merge, and closure authority.

The model you choose for the review command session stays the reviewer and manager. It owns the shared revision packet, checks that Standards and Spec are complete, verifies every candidate finding, reconciles them across axes, publishes the verdict, and alone merges, labels, promotes, and closes. At the start of each `/review-this` run it uses the optional configured `review-fixer` subagent, whose model is user-owned configuration, for at most one fix round. If the fix subagent is unavailable, the review publishes its findings and stops. The fix subagent may edit and run focused tests only in the current checkout; it cannot commit, push, publish a verdict, merge, label, promote, or close. One corrected fix packet is allowed inside the existing fix budget; continued failure stops the ticket with `needs-info` and never silently hands the work back to the frontier model. Required Standards category statuses travel through the review adapter and are checked before reconciliation; a finding missing a category or severity is rejected, never invented as a blocking correctness finding. One frontier pass reports Standards and Spec separately, and identical defects reported twice count once with the clearest evidence kept. Test strategy, accessibility, observability, migration, and simplification run as triggered checks inside Standards, not new review axes, and at most one specialist supplements a full-review round: security for the strongest trust-boundary risk, or web performance for measured web-performance work.

The three workflow skills agree on state because they share one decision module. It looks at GitHub facts and pull-request facts, then returns the next safe actions: label changes, review freshness, merge eligibility, verdict reuse, and parent completion. Labels follow the blockers. Every installed skill carries the same copy of this module.

The workflow commands now consume the bounded orientation contract directly: `plan-this` resolves an orientation set for each proposed ticket before publication approval and rejects an over-budget ticket, `implement-this` resolves current sources in the current checkout before broad documentation loading, and `review-this` resolves orientation sources once per pinned head-and-base pair and shares the compact evidence across Standards and Spec. The compact evidence stays small — task band, resolved bytes, cap, source count, cache-gap state — and exact source lists appear only on failure or approved substitution; an over-budget review set stops before broad loading and reports its exact sources.

A ticket starts only when its native GitHub blockers are closed. Every ticket delivers by pull request against `main`: the run pushes the feature branch, opens one pull request with `Closes #<ticket>`, and upserts compact evidence into the pull-request body, and the squash-merge closes it. No path pushes directly to `main`.

Accepted criteria keep one stable identity across planning, implementation, and review. `plan-this` publishes each criterion with a local ID unique within its own issue, written `AC-1`; the stable criterion key is the authority issue number plus that local ID, so two issues may both use `AC-1`. Clearer wording keeps the same ID, changed observable behavior gets a new ID and retires the old, and retired IDs are never reused or accepted as active evidence. `implement-this` proves criteria by ID rather than by full sentence text, with compact evidence in the pull-request body. Review keeps the same key: Spec findings name `#<issue>:AC-N`, never prose.

The three skills form the complete workflow. `plan-this` publishes the parent specification and native child tickets; `implement-this` implements one ticket in the current checkout; `review-this <target>` runs one frontier Standards-plus-Spec pass before merge, promotion, and closure. GitHub keeps enough state to resume from the parent specification after any pause.

The accepted command-session design starts implementation and review independently whenever each stage has work. Each run owns exactly one ticket or pull request in the current checkout with no worker lifecycle to manage. There is no supervisor or coordinator. ADR-0019 records these rules. ADR-0031 replaces the worker-wave contract with single-target current-checkout runs.

### Single-target runs own their checkout (ADR-0031)

There are no worker sessions to stop and no worktrees to clean up. There are no sessions to stop and no worktrees to remove. Delivery lives on GitHub as an open pull request with a valid closing reference and compact evidence. A merged pull request closes its ticket through the closing reference. Existing Agent Manager worktrees are user-managed outside these commands. ADR-0023 narrows the ADR-0019 cleanup rule.

### Performance contract shipped in #157

Planning now records `ordinary` or `high-risk` before publication. A high-risk trigger with evidence missing is an internal incomplete result that stops publication and risk labeling until the evidence lands. Ordinary tickets target 60 minutes from reservation to terminal outcome; high-risk tickets target 90 minutes. Implementation runs the ticket's smallest sufficient focused checks and upserts compact evidence into the pull-request body; it never runs the full repository gate.

Review starts when a pull request has current head and base revisions plus implementation evidence. One frontier pass covers the initial revision, one delta review covers a later revision, and at most one automatic fix round runs per pull request. Safe advisories join blocking fixes, advisory-only findings are deferred, and final-verification repairs receive a bounded rereview. SLO misses remain visible without relaxing safety gates. Before review publication and before merge the current issue bodies are hashed over their authoritative sections and compared with the requirements revision the delivery evidence pinned; a changed body stops the ticket with `needs-info` until it is reconciled and the run resumes.

### Compact evidence replaces the worker contract (ADR-0031)

Each run proves every active acceptance criterion by its stable local ID: behavioral criteria show focused passing proof, non-behavior criteria record a narrow rationale, bug fixes add defect-specific RED, and extra proof is required only when the ticket names it.

### Frontier review authority shipped with ADR-0022

Issue #173 keeps the review trust boundary with the frontier command session: it owns revision packets, completeness, finding verification, reconciliation, verdict publication, merge, labels, promotion, and closure. No execution model is selected; the optional configured `review-fixer` subagent edits and runs focused tests only and cannot publish verdicts or change tracker state. The adapter now transports required Standards category statuses, missing category or severity never becomes a blocking correctness finding, deduplication preserves axis identity, and at most one specialist supplements a full-review round. ADR-0031 closes the worker-wave chapter: one ticket or pull request runs in the current checkout.
### Ticket-named proof replaces triggered profiles (ADR-0031)

Extra browser, security, migration, operability, compatibility, or performance proof is required only when the ticket's acceptance criteria, risk, constraints, or smallest verification explicitly names it. Planning keeps its existing fields and adds no quality-profile checklist. Unexpected failures follow a bounded reproduce, isolate, one-hypothesis, smallest-fix, regression-proof loop. The comparison source is pinned to the Addy Osmani `agent-skills` revision `f63ec56a3cc936408d792956ae583c3c96a825bd`, recorded with adopt, adapt, reject, and reference-only dispositions in `reference/vendor-facts.md`; no Addy source is a runtime dependency.

### Accepted command-session example

A specification has five tickets: #101 and #102 have no blockers, #103 is blocked by #101, #104 is blocked by #101 and #102, and #105 is blocked by #103.

1. Plan grills the open decision frontier, gets publication approval, and publishes the parent #100 and five children. #101 and #102 get `ready-for-agent`; #103-#105 get `blocked`.
2. Run `/implement-this #101` in the current checkout to implement one ticket and deliver one pull request.
3. Review that pull request with `/review-this <pr>` or `/review-this #101` when the issue resolves to exactly one open pull request. It verifies local findings against the current head and merges the pull request when eligible. When #101 closes, it promotes #103 to `unblocked` + `ready-for-agent`; when #101 and #102 close, it also promotes #104.
4. Each later ticket waits for its own explicit invocation. The review run owns that single pull request through merge.
5. When the pull request merges, its closing reference closes the ticket with no post-merge verification and no whole-spec review. A cross-ticket defect becomes the smallest follow-up child ticket; otherwise the parent #100 closes.
