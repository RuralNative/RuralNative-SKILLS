The technical flow starts with a task you give to `/plan-this`.

1. Planning loads repository-owned `unslopify` before progress and reads only the focused agent cache `AGENTS.md -> ARCHITECTURE.md -> seam leaf -> CONTEXT.md -> relevant ADRs`; human pages remain derived and are not preloaded. Once `unslopify` has set itself up in a project, it loads before the first reply of every session (ADR-0029). Each task's read set resolves at runtime from affected seams and is capped in UTF-8 bytes, so unrelated documentation growth never changes what one task must read.
2. Planning defines an intent capsule (`Outcome`, `User`, `Why now`, `Success`, `Constraints`, `Non-goals`) and asks a question only when repository facts and the confirmed task cannot decide a choice that changes product behavior, scope, cost, risk, or an action that is hard to undo; a complete settled capsule moves on without a question. It optionally explores three directions when the solution form is unsettled, then resolves the remaining choices one at a time in one plain sentence with at most three short options and one short recommendation, researches facts the codebase can answer, shows a plain-language preview of what will be created, the main risks, and what happens next, and waits for explicit publication approval. Interrupted runs resume recorded decisions. One-decision precedence and the planning-only write boundary are explicit.
3. Planning publishes a parent specification with no claimable label, links each child ticket to it as a native GitHub sub-issue, and creates native blocked-by edges from each blocker's numeric database ID. Every published criterion carries a local ID unique within its own issue, written `AC-1`; the stable key is the authority issue number plus the local ID, and retired IDs are never reused. Independent tickets start together, real blockers become edges, and file overlap without semantic dependency becomes a scheduling note for user-managed parallel checkouts.
4. You run `/implement-this` with one ready ticket. The invocation validates that single ticket before any write and stops on multiple references, parent specifications, or pull requests. It stops while the ticket has an open native blocker. The run validates the single ticket before any write, creates no worktree, worker, or session, reads no Agent Manager overview and issues no worker-management calls — with the tracked `task: ask` permission posture; a dirty checkout or branch mismatch stops the run before any write.
5. The run loads `unslopify` under the same prose contract and focused cache, resolves its orientation set from the ticket's affected seams in the checkout before broad documentation loading and records the compact evidence (task band, resolved bytes, cap, source count, cache-gap state), classifies every active acceptance criterion by its stable local ID as behavioral with focused passing proof or non-behavior with a narrow rationale, records defect-specific RED for bug fixes, adds extra proof only when the ticket names it, renders one compact evidence block that never accepts a retired criterion ID as active evidence, and runs exactly the ticket's smallest sufficient focused checks. The loaded `unslopify` also audits everything the run writes on its own, silently while it works and before it publishes, and an explicit audit request still returns the full report (ADR-0016, ADR-0026).
6. Delivery is always a pull request. The run pushes the feature branch and opens one pull request against `main` with `Closes #<ticket>` in its body; compact evidence lands in that body, and the ticket closes only when the pull request merges. Nothing pushes directly to `main`.
7. Review is a separate stage. You start `/review-this <target>` in the checkout matching the pull request whenever review work exists. The target is one pull-request number, one pull-request URL, or one issue number or URL resolving to exactly one open pull request, and bare and hash numbers normalize to the same number. The resolver turns that target into exactly one open pull request before any write happens, and a malformed, missing, closed, ambiguous, parent-specification, multiple, or cross-repository target stops with a named reason. The selected pull request must be open, close the ticket it is linked to, and carry current head and base revisions matching the checkout. The frontier reviewer owns the revision packet, Standards and Spec completeness, finding verification, verdict publication, merge, labels, promotion, and closure, and it uses the optional configured `review-fixer` subagent for at most one fix round. One pull request reviews at a time in the current checkout with no dispatch plan, no worker reuse, and no capacity deferral. No cloud collection runs; one frontier Standards-plus-Spec pass reviews the pinned head and base. One frontier pass reads the pinned head-and-base pair once, so no context repeats discovery. Spec findings cite the same stable criterion key planning and implementation evidence used — the authority issue number plus the local ID (`#<issue>:AC-N`) — never the full sentence text. Orientation sources resolve once per pinned revision pair and the compact evidence is shared across both axes without publishing full path lists on success; an over-budget set stops before broad loading and reports its task band, resolved bytes, cap, source count, and exact sources. The single pull request proceeds through review, at most one fix round, publication, and merge. Required Standards category statuses travel through the local review adapter and are checked before reconciliation; a finding missing category or severity is rejected, never invented as a blocking correctness finding, and Standards and Spec stay separate even at the same location. No worktrees or workers are created; the optional fix round uses the configured `review-fixer` subagent after explicit approval via the `task: ask` gate. The fix subagent edits and runs focused tests only and cannot commit, push, publish a verdict, or change merge, label, promotion, closure, or parent state; remaining blocking findings stop the run with a pinned report. A direct pull-request target keeps its closing issue for review context but cannot auto-merge when its linked ticket disagrees. The skill metadata and installation guide use the same target syntax as this resolver.
8. In the accepted design, implementation and review command sessions manage their own frontiers. The run validates one ticket, works in the current checkout, and treats an open pull request with compact body evidence as delivery. The #157-#158 worker-wave additions are superseded by ADR-0031. Review starts when the PR has current revisions and implementation evidence, pins findings to the head and base, batches safe advisories with blocking fixes, and stops on checkout mismatch instead of creating another worktree. The `task: ask` gate keeps the optional fix round after explicit approval and never edits `.kilo/agent-manager.json`. Target resolution shipped with #156. Under ADR-0031 no worker stays live and no worktree is retained: each run owns one ticket or pull request in the current checkout.

### Accepted command-session stage example

Tickets #101 and #102 start ready; #103 waits on #101; #104 waits on #101 and #102; #105 waits on #103. In the accepted design, run `/implement-this #101` in the current checkout to implement one ticket and deliver one pull request. Review that pull request with `/review-this <pr>` or `/review-this #101` when the issue resolves to exactly one open pull request. Merges promote #103 and #104 as their blockers close. After promotion, newly unblocked tickets wait for their own explicit invocations. The parent closes only when every child is closed.

ADR-0031 supersedes the worker-wave shipments of #155–#158.

#157-#158 add measured risk and review flow: planning records each ticket's class, implementation measures setup and affected-test evidence, and review starts as soon as a PR has current revisions and delivery evidence. One frontier pass hosts the initial full review, with one delta review after the single fix round. A pinned verdict records head, base, requirements revision, and review-policy revision for reuse.

One rule protects every step above: text flowing through the workflow, including task descriptions, issue bodies, comments, specifications, and review comments, is treated as requirements data. It says what to build and carries evidence, but it cannot widen scope, pick files, authorize tools, or override gates. Runs never download skills mid-flight; installing skills is outside the run.

Requirements stay fresh by fingerprint, not by memory. Before delivery and before review, the current parent and ticket bodies are hashed over their authoritative sections — affected seams, criterion IDs and text and status, structural constraints, blockers, settled decisions, risk, and verification intent — and the result is compared to the revision the compact evidence pinned. A changed body stops the ticket with `needs-info` until the body is reconciled and whoever runs the work resumes it; comments and evidence never enter the hash, and a requirement mentioned in a comment counts only after it is copied into the issue body.

All three workflow skills share one small decision module, the pure workflow state core. It reads ticket and pull-request facts and returns the next safe actions: label changes, review freshness, merge eligibility, verdict reuse, and parent completion.

GitHub remains the task record. Native blockers decide what may start, and closure happens only after delivery is proven.

The documentation flow has its own rules. Every lifecycle run opens by settling the tier, the private diagnostics consent, and the decision frontier, then does the branch's work; a tier promotion applies in the same run and never happens in reverse. Agents update a seam's technical leaf with the seam, review that seam's affected claims against the code, refresh its stored code fingerprint, then regenerate these human pages from authored documents. Loading budgets are caps on orientation documents, so an agent states its goal, reads only the matching row, and uses a named cache gap before widening the read set. These pages are for people and are never the source of technical truth.
