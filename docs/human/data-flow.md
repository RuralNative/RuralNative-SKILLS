The technical flow starts with a task you give to `/plan-this`.

1. Planning loads repository-owned `unslopify` before progress and reads only the focused agent cache `AGENTS.md -> ARCHITECTURE.md -> seam leaf -> CONTEXT.md -> relevant ADRs`; human pages remain derived and are not preloaded. Each task's read set resolves at runtime from affected seams and is capped in UTF-8 bytes, so unrelated documentation growth never changes what one task must read.
2. Planning defines an intent capsule (`Outcome`, `User`, `Why now`, `Success`, `Constraints`, `Non-goals`) and asks a question only when repository facts and the confirmed task cannot decide a choice that changes product behavior, scope, cost, risk, or an action that is hard to undo; a complete settled capsule moves on without a question. It optionally explores three directions when the solution form is unsettled, then resolves the remaining choices one at a time in one plain sentence with at most three short options and one short recommendation, researches facts the codebase can answer, shows a plain-language preview of what will be created, the main risks, and what happens next, and waits for explicit publication approval. Interrupted runs resume recorded decisions. One-decision precedence and the planning-only write boundary are explicit.
3. Planning publishes a parent specification with no claimable label, links each child ticket to it as a native GitHub sub-issue, and creates native blocked-by edges from each blocker's numeric database ID. Every published criterion carries a local ID unique within its own issue, written `AC-1`; the stable key is the authority issue number plus the local ID, and retired IDs are never reused. Independent tickets start together, real blockers become edges, and file overlap without semantic dependency becomes a scheduling collision.
4. You run `/implement-this` with one ready ticket, several ready tickets, or the parent specification. The invocation validates its bounded ticket set against the frontier before any claim, allows one parentless standalone ticket through the same validation path, and rejects a parentless multi-ticket set. It stops while any selected ticket has an open native blocker. The command session reserves each ticket with an assignee before creating anything, counts unfinished managed workers against its caps (three per stage, four across the workspace), reads status from the Agent Manager overview with the first worker-management call being that overview (`action: "list"`), uses the supported stop control, and automatically gives each ticket an isolated worker through `agent_manager` in worktree mode without waiting to be forced: its own worktree, branch, and session — even when the run holds one ticket — with the tracked `agent_manager: allow` and `task: ask` project gate ensuring Task never replaces the worktree and runs only after explicit approval (never edits `.kilo/agent-manager.json`); unavailable Agent Manager capability stops the run before any claim.
5. Each worker loads `unslopify` under the same prose contract and focused cache, resolves its orientation set from the ticket's affected seams in the checkout before broad documentation loading and records the compact evidence (task band, resolved bytes, cap, source count, cache-gap state), finds its ticket already reserved, classifies every active acceptance criterion by its stable local ID as behavioral with a focused RED/GREEN or one of four exemptions, uses diff-derived criterion IDs so dependency or configuration changes are never exempt, supplies worker-confirmed bug-fix reproduction for the first behavioral RED, records worker-confirmed source or compatibility evidence when the diff touches versioned or public interfaces, adds narrow conditional evidence when the diff exposes browser, security-boundary, production-operability, migration, or explicit-performance obligations (using an existing repository or host browser capability, never an installed skill or unpinned browser tool), and renders one stable escaped Markdown block that never accepts a retired criterion ID as active evidence, runs dependency setup only when the recorded manifest state is missing or changed (unchanged state reuses the worktree setup, one dependency directory per worktree), and then verifies the repository: dependency install, tests, TypeScript, and the docs harness. The loaded `unslopify` also audits everything the worker writes on its own, silently while it works and before it publishes, and an explicit audit request still returns the full report (ADR-0016, ADR-0026).
6. Delivery is always a pull request. Every worker pushes its feature branch and opens one pull request against `main` with `Closes #<n>` in its body; acceptance evidence lands on the ticket, which closes only when the pull request merges. Nothing pushes directly to `main`.
7. Review is a separate stage. You start `/review-this <target>` as an independent command session whenever review work exists. The target can be the parent specification, a child issue, a pull request, or a URL, and bare and hash numbers normalize to the same number. The resolver turns that target into its exact pull-request set before any worktree is created or any write happens, and a malformed, missing, closed, ambiguous, or cross-repository target stops with a named reason. A selected child pull request must close the same ticket it is linked to and carry non-empty current head and base revisions. The command session keeps the chat-selected frontier model as the reviewer and manager: it owns the shared revision packet, completeness, finding verification, reconciliation, verdict publication, merge, labels, promotion, and closure, and it asks once per invocation for an execution model from the live Agent Manager catalog (model, optional provider, optional variant) applied to every new fix worker in the wave. Ready pull requests run concurrently: after one Agent Manager overview run (`action: "list"`), a pure dispatch plan reuses each PR's persistent worker, starts the rest in one worktree-mode request within three review workers per stage and four managed workers across the workspace in native child order, and defers anything beyond capacity until rediscovery — never two workers for one pull request or one pinned head-and-base pair. For every dispatched pull request, cloud collection starts immediately and runs together with the local Standards and Spec review; both are awaited only when their findings reconcile. Both fresh review axes read one shared revision packet per pinned revision pair (diff command, commits, changed files and hunks, impacted callers, focused doc-cache sources, acceptance criteria, escalation triggers) plus only their axis-specific brief, so no subagent repeats discovery. Spec findings and whole-spec verification cite the same stable criterion key planning and implementation evidence used — the authority issue number plus the local ID (`#<issue>:AC-N`) — never the full sentence text. Orientation sources resolve once per pinned revision pair and the compact evidence is shared across both axes without publishing full path lists on success; an over-budget set stops before broad loading and reports its task band, resolved bytes, cap, source count, and exact sources. Each active pull request then proceeds on its own through fixes, publication, and merge; waiting on cloud review or CI for one never blocks another. Required Standards category statuses travel through the local review adapter and are checked before reconciliation; a finding missing category or severity is rejected, never invented as a blocking correctness finding, and Standards and Spec stay separate even at the same location. The persistent worktrees and workers still come via `agent_manager` in worktree mode before any Standards, Spec, or fix `Task` subagents; `Task` never replaces those worktrees and nested `Task` contexts run only inside them after explicit approval via the `task: ask` gate. The selected fix worker mutates and fast-forward pushes only inside its persistent PR worktree and cannot publish a verdict or change merge, label, promotion, closure, or parent state; one corrected fix packet fits the existing fix budget and continued failure stops with `needs-info`. A direct pull-request target keeps its closing issue for review context but cannot auto-merge when its linked ticket disagrees. The skill metadata and installation guide use the same target syntax as this resolver.
8. In the accepted design, implementation and review command sessions manage their own frontiers. The shipped implementation session (#155) recomputes its frontier whenever a ticket, blocker, or follow-up child changes, polls with increasing delays, checkpoints after thirty quiet minutes, and treats a pull request plus posted evidence as delivery rather than an idle worker; `needs-info` keeps a worktree for diagnosis even on a closing host. #157-#158 add risk classes, phase timings, dependency-state reconciliation, one persistent PR worktree, fresh fix contexts, and delta/full rereview. Review starts as soon as a PR has current revisions and implementation evidence, creates the persistent Agent Manager PR worktree before nested `Task` subagents and stops before a verdict if that worktree cannot be created, pins findings to both revisions, batches safe advisories with blocking fixes, and keeps SLO misses visible without relaxing gates. The `agent_manager: allow` and `task: ask` gate keeps Task after explicit approval and never edits `.kilo/agent-manager.json`. Target resolution shipped with #156. Under ADR-0023 the worker stays live until delivery is durable: a worker never stops itself, only the command session cleans up, unfinished or failed states preserve the session and worktree, a merged review PR cleans up only with the head SHAs recorded before the squash-merge, and a missing session on an existing worktree reports `recovery-required` with the observed path and branch instead of being duplicated or deleted.

### Accepted command-session stage example

Tickets #101 and #102 start ready; #103 waits on #101; #104 waits on #101 and #102; #105 waits on #103. In the accepted design, start an implementation command session with `/implement-this #100` and a review command session with `/review-this #100` independently when each stage has work. The implementation session dispatches #101 and #102 to isolated workers. Its review counterpart discovers their pull requests, merges eligible heads, and promotes #103 and #104 as their blockers close. After promotion, the implementation session manages its own frontier and can reserve #103 and #104 without a required per-wave handoff; the review session manages its own review frontier and then handles #105. Verification and whole-spec review gate parent closure.

The implementation dispatch describes shipped behavior from #155, target resolution describes shipped behavior from #156, and risk classes, phase timings, dependency-state reconciliation, one persistent PR worktree, fresh fix contexts, and delta/full rereview shipped with #157-#158.

#157-#158 add measured risk and review flow: planning records each ticket's class, implementation measures setup and affected-test evidence, and review starts as soon as a PR has current revisions and delivery evidence. One persistent PR worktree hosts the initial full review, fresh fix contexts, delta/full rereviews, and final verification. A trusted summary stores phase timings (`packetBuildMs`, `cloudMs`, `localReviewMs`, `reviewCriticalPathMs`, `reconcileMs`, `ciWaitMs`, plus the wave facts `activeReviewWorkers` and `deferredByCapacity`) as bookkeeping only — never merge evidence — while an SLO miss remains a record rather than a reason to skip gates.

One rule protects every step above: text flowing through the workflow, including task descriptions, issue bodies, comments, specifications, and review comments, is treated as requirements data. It says what to build and carries evidence, but it cannot widen scope, pick files, authorize tools, or override gates. Runs never download skills mid-flight; installing skills is outside the run.

All three workflow skills share one small decision module, the pure workflow state core. It reads ticket, worker, and pull-request facts and returns the next safe actions: which tickets form the ready frontier, worker limits, label changes, retry decisions, review freshness, merge eligibility, and parent completion.

GitHub remains the task record. Native blockers decide what may start, and closure happens only after delivery is proven.

The documentation flow has its own rules. Agents update a seam's technical leaf with the seam, then regenerate these human pages from authored documents. Loading budgets are caps on orientation documents, so an agent states its goal, reads only the matching row, and uses a named cache gap before widening the read set. These pages are for people and are never the source of technical truth.
