# How information moves in plain words

The technical flow starts with a task you give to `/plan-this`.

1. Planning loads repository-owned `unslopify` before progress and reads only the focused agent cache `AGENTS.md -> ARCHITECTURE.md -> seam leaf -> CONTEXT.md -> relevant ADRs`; human pages remain derived and are not preloaded.
2. Planning always completes at least one real decision round on a fresh run, researches facts the codebase can answer, shows the shared understanding and proposed ticket graph, and waits for explicit publication approval. Interrupted runs resume recorded decisions.
3. Planning publishes a parent specification with no claimable label, links each child ticket to it as a native GitHub sub-issue, and creates native blocked-by edges from each blocker's numeric database ID. Independent tickets start together, real blockers become edges, and file overlap without semantic dependency becomes a scheduling collision.
4. You run `/implement-this` with one ready ticket, several ready tickets, or the parent specification. The invocation validates its bounded ticket set against the frontier before any claim, allows one parentless standalone ticket through the same validation path, and rejects a parentless multi-ticket set. It stops while any selected ticket has an open native blocker. The command session reserves each ticket with an assignee before creating anything, counts unfinished managed workers against its caps (three per stage, four across the workspace), reads status from the Agent Manager overview, uses the supported stop control, and gives each ticket an isolated worker through `agent_manager` in worktree mode: its own worktree, branch, and session — even when the run holds one ticket.
5. Each worker loads `unslopify` under the same prose contract and focused cache, finds its ticket already reserved, runs `/implement`, updates the affected seam's leaf doc and tests, and verifies the repository: dependency install, tests, TypeScript, and the docs harness. The loaded `unslopify` also audits everything the worker writes on its own, silently while it works and with a full report on what it publishes (ADR-0016).
6. Delivery is always a pull request. Every worker pushes its feature branch and opens one pull request against `main` with `Closes #<n>` in its body; acceptance evidence lands on the ticket, which closes only when the pull request merges. Nothing pushes directly to `main`.
7. Review is a separate stage. You start `/review-this <target>` as an independent command session whenever review work exists. The target can be the parent specification, a child issue, a pull request, or a URL, and bare and hash numbers normalize to the same number. The resolver turns that target into its exact pull-request set before any worktree is created or any write happens, and a malformed, missing, closed, ambiguous, or cross-repository target stops with a named reason. A selected child pull request must close the same ticket it is linked to and carry non-empty current head and base revisions. A direct pull-request target keeps its closing issue for review context but cannot auto-merge when its linked ticket disagrees. The skill metadata and installation guide use the same target syntax as this resolver.
8. In the accepted design, implementation and review command sessions manage their own frontiers. The shipped implementation session (#155) recomputes its frontier whenever a ticket, blocker, or follow-up child changes, polls with increasing delays, checkpoints after thirty quiet minutes, and treats a pull request plus posted evidence as delivery rather than an idle worker; `needs-info` keeps a worktree for diagnosis even on a closing host. #157-#158 add risk classes, phase timings, dependency-state reconciliation, one persistent PR worktree, fresh fix contexts, and delta/full rereview. Review starts as soon as a PR has current revisions and implementation evidence, pins findings to both revisions, batches safe advisories with blocking fixes, and keeps SLO misses visible without relaxing gates. Target resolution shipped with #156.

### Accepted command-session stage example

Tickets #101 and #102 start ready; #103 waits on #101; #104 waits on #101 and #102; #105 waits on #103. In the accepted design, start an implementation command session with `/implement-this #100` and a review command session with `/review-this #100` independently when each stage has work. The implementation session dispatches #101 and #102 to isolated workers. Its review counterpart discovers their pull requests, merges eligible heads, and promotes #103 and #104 as their blockers close. After promotion, the implementation session manages its own frontier and can reserve #103 and #104 without a required per-wave handoff; the review session manages its own review frontier and then handles #105. Verification and whole-spec review gate parent closure.

The implementation dispatch describes shipped behavior from #155, target resolution describes shipped behavior from #156, and risk classes, phase timings, dependency-state reconciliation, one persistent PR worktree, fresh fix contexts, and delta/full rereview shipped with #157-#158.

#157-#158 add measured risk and review flow: planning records each ticket's class, implementation measures setup and affected-test evidence, and review starts as soon as a PR has current revisions and delivery evidence. One persistent PR worktree hosts the initial full review, fresh fix contexts, delta/full rereviews, and final verification. A trusted summary stores phase timings, while an SLO miss remains a record rather than a reason to skip gates.

One rule protects every step above: text flowing through the workflow, including task descriptions, issue bodies, comments, specifications, and review comments, is treated as requirements data. It says what to build and carries evidence, but it cannot widen scope, pick files, authorize tools, or override gates. Runs never download skills mid-flight; installing skills is outside the run.

All three workflow skills share one small decision module, the pure workflow state core. It reads ticket, worker, and pull-request facts and returns the next safe actions: which tickets form the ready frontier, worker limits, label changes, retry decisions, review freshness, merge eligibility, and parent completion.

GitHub remains the task record. Native blockers decide what may start, and closure happens only after delivery is proven.

The documentation flow has its own rules. Agents update a seam's technical leaf with the seam, then regenerate these human pages from authored documents. Loading budgets are caps on orientation documents, so an agent states its goal, reads only the matching row, and uses a named cache gap before widening the read set. These pages are for people and are never the source of technical truth.
