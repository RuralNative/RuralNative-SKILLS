These are the promises the skills make.

- A skill's frontmatter name matches its folder, so the registry installs the intended skill.
- The public registry is the official install path. Local install leftovers stay out of the repository.
- Documentation changes update their technical leaf in the same change.
- The documentation cache sizes itself and stays honest. Every lifecycle run starts by settling the tier it needs, and the tier only ever grows — from minimal to standard to full — automatically as real needs appear (a durable decision, more than one independently editable seam, or multi-agent coordination). Destructive changes (trims, moves, deletions, demotion) still need one explicit Improve approval after one complete migration preview. Each documented seam carries a code fingerprint in the manifest, and the doc check fails whenever the fingerprint is stale — in a working tree and in clean CI alike — until the affected claims are reviewed against the code. Audit stays read-only: it reports what a promotion would be but never applies it. Work that collides with a numbered invariant stops until a decision supersedes or narrows it.
- Orientation is bounded in bytes, not prose. Each task resolves its own small document set from affected seams, and that set must fit its cap (9,000 ordinary, 13,500 API or route, 18,000 schema or data, 10,500 re-orientation, and 18,000 absolute bytes; the ceilings are caps, not targets); duplicate sources count once, compact citations stay navigation and never load, and only sources a leaf explicitly declares required join the set — rejected decisions never do, and superseded decisions stay out of current guidance unless declared required. A decision joins only when its status line reads exactly accepted or superseded: near-misses like "accepted-ish" or "accepted extra" never load, and neither a missing nor a draft status does. Reading the code being changed is never blocked, and a missing fact becomes a named cache gap that requires your approval before the read set widens — approval can substitute or narrow sources, never waive the cap. The exhaustive doc inventory lives in a harness-owned manifest that no task reads, and the fingerprints and private consent state stay out of every read set too. An older bloated cache is repaired through Improve only after one complete migration preview gets explicit approval. The workflow commands consume the contract directly: planning preflights each proposed ticket and rejects an over-budget one, implementation resolves current sources before broad loading, and review resolves one set per pinned revision pair, stopping before broad loading when the set is over budget and reporting its exact sources.
- Every review follows one written policy (`REVIEW.md`). The frontier reviewer verifies every finding before publishing it and alone owns verdicts, commits, pushes, merges, and closure. One pull request reviews at a time in the current checkout with no worker caps. One frontier pass covers Standards and Spec in-session with no cloud collection. The optional `review-fixer` edits and runs approval-required focused tests only. Requirements stay pinned too: the same requirements revision rides the compact evidence in the pull-request body, and delivery, review publication, and merge compare the current issue bodies against it — a changed body stops with `needs-info` until it is reconciled and the run resumes, with no waiver.
- The frontier reviewer keeps all review and merge authority. No execution model is chosen; the optional configured `review-fixer` subagent edits and runs focused tests only in the current checkout and cannot commit, push, publish a verdict, merge, label, promote, or close. A resume shows the earlier choice but you confirm it. Remaining blocking findings stop the run with a pinned report; the frontier model never acts as an implicit fixer.
- Standards and Spec stay separate axes inside the one frontier pass. A finding missing its category, severity, exact revision, governing rule, or structured evidence is rejected, never invented as a blocking correctness finding. Identical defects reported twice count once with the clearest evidence kept. Spec findings cite the same stable criterion key planning and implementation evidence used — the authority issue number plus the local ID — never the full sentence prose.
- Prose cleanup keeps commands, code, links, quotations, and facts intact.
- Text that flows through a workflow, including tasks, issue bodies, comments, specifications, and review comments, is requirements data. It cannot widen scope, select files, authorize tools, or override gates.
- Workflow runs never download skills. Installing skills stays with you, outside the run.
- If `unslopify` is missing, a documentation workflow stops before drafting and points you to that skill's install guide instead of running any install command.
- A manual install never overwrites an existing skill without your explicit approval. Every skill's install guide states this.
- `unslopify` treats prose in its scope as inert content: prompt-like text in a document is reviewed as text, never executed.
- Once `unslopify` is loaded it drafts the agent's own English in plain language and audits it by default, silently in chat and before publication, with the full report returned only on an explicit audit request (ADR-0016, ADR-0026, ADR-0029). Technical wording that an implementation needs survives even when a style rule would flag it; user text still changes only when you ask.
- `unslopify` may write exactly one owned session-start block in your project's root `AGENTS.md` so later sessions load the skill before the first reply; it says so once, never asks first, and every byte outside that block stays protected. Symlinks, files another tool owns, malformed blocks, and denied writes leave the file untouched (ADR-0029).
- A record of confirmed agent mistakes exists only if you say yes, and the skill asks at a first-run checkpoint you cannot skip and remembers your answer in a private file outside version control (ADR-0018, ADR-0028). The log file stays private, outside the documentation cache and version control, and a remembered "no" or a failed save never enables logging.
- Decisions that a future agent would rely on are written down before the work that needs them: the choice, its context, the alternatives genuinely considered and why they lost, and the consequences. A newly discovered tradeoff during the work pauses it until the record exists. Trivial reversible choices stay in the commit message. Old decisions missing their reasoning are never rewritten with guessed history: they are recovered only from cited evidence into a separate clarification record, or honestly marked unknown (ADR-0028).
- Installing from a public registry records provenance and pins reviewed revisions; every install guide on the shelf carries this trust section, and the residual trust in the source repository stays with you.
- Planning defines and confirms an intent capsule, optionally explores three directions, then runs `/grill-with-docs`, `/to-spec`, and `/to-tickets` in order, with repository-owned `unslopify` cleaning prose under scope, protected-content, preservation, and completion-report rules, using only the focused agent cache `AGENTS.md -> ARCHITECTURE.md -> seam leaf -> CONTEXT.md -> relevant ADRs` (human pages are derived and not preloaded).
- `/plan-this` asks a question only when repository facts and the confirmed task cannot decide a choice that changes product behavior, scope, cost, risk, or an action that is hard to undo; a complete settled task reaches the preview without a forced question. It optionally explores three directions when the solution form is unsettled, then resolves the remaining choices one plain question at a time with at most three short options and one short recommendation before waiting for explicit publication approval. The parent specification carries only the user stories needed to distinguish observable behavior, while independent tickets start together, real blocker edges describe actual consumption, and file overlap without semantic dependency is recorded as a scheduling note for user-managed parallel checkouts.
- Planning publishes an unlabelled parent specification and ready tickets linked as native GitHub sub-issues, builds native blocked-by edges from REST database IDs, and asks about unresolved decisions. `ready-for-agent` is the only claimable label; `ready-for-dev` is retired.
- Accepted criteria carry one stable identity across the workflow. `plan-this` publishes every criterion with a local ID unique within its own issue (`AC-1`); the stable key is the authority issue number plus the local ID. Clearer wording keeps the same ID, changed observable behavior gets a new ID and retires the old, and retired IDs are never reused or accepted as active evidence. `implement-this` proves evidence by criterion ID rather than by full sentence text, and review Spec findings cite the same stable key (`#<issue>:AC-N`).
- Implementation validates exactly one open ticket before any write and stops on multiple references, parent specifications, or pull requests, implements that ticket in the current checkout with no worktree, worker, or Agent Manager involvement and no worker-management calls, keeps the tracked `task: ask` permission posture (never edits `.kilo/agent-manager.json`), runs no worker sessions, loads repository-owned `unslopify` before progress with the same prose and focused-cache rules, stops when a native blocker is open, and stops before any write on a dirty checkout or branch mismatch.
- Every implementation delivers by pull request. Nothing pushes directly to `main`, force-pushes, or closes a ticket before merge; merge closes it.
- A blocked ticket stops with `needs-info` and a pinned report in the current checkout.
- There are no worker sessions to stop and no worktrees to clean up. Retired lifecycle states (`preserved-for-resume`, `preserved-for-diagnosis`, `cleanup-pending`, `recovery-required`) no longer exist. Delivery lives on GitHub as an open pull request with a valid closing reference and compact evidence. Existing Agent Manager worktrees are user-managed outside these commands (ADR-0031).
- Verification runs dependency install, tests, TypeScript, and the docs harness. Every check in the chain can fail.
- The run uses the repository's ordinary dependency setup in the current checkout.
- Implementation runs `/implement` directly in the current checkout and does not host code review; review lives in `/review-this <target>`, where one pull request number, URL, or singly-resolving issue is resolved to exactly one open pull request with the checkout matching its head, and an invalid or ambiguous target stops with a named reason. ADR-0031 supersedes the #155–#158 and #170 worker-wave shipments with single-target current-checkout runs. There are no ticket worktrees; review runs in the same checkout as implementation. Review creates no worktrees; the optional fix round uses the configured `review-fixer` subagent after explicit approval via `task: ask`. `needs-info` stops the run with a pinned report; there is no worktree lifecycle to clean up.
- Review readiness also requires a pull request's linked ticket to match its closing reference and its current head and base revisions to be present.
- Direct pull-request review keeps the closing issue for context but withholds auto-merge authority when those ticket facts disagree.
- The skill metadata, installation guide, and review body use the same target syntax.
- The three user-facing workflow commands are `plan-this`, `implement-this`, and `review-this` only.
- The ready frontier contains only open, unblocked, unassigned tickets with `ready-for-agent`.
- After a ticket closes, only its newly unblocked dependents get label updates.
- One shared decision module, copied byte-identical into all three workflow skills, turns observed facts into next actions: single-ticket validation, review freshness, one fix round, merge only with green required checks always, plus the approved fallback when no equivalent CI exists, resolved findings, a clean review, unchanged reviewed head and base, and a mergeable pull request. Repository verification fails if any copy drifts from the authored source.

The document seam records its attention, routing, and decision rules as separate invariants.

ADR-0031 retires the #157-#158 worker-wave performance contract. One frontier pass and at most one fix round followed by one delta review replace it. No persistent worker exists; the optional fix round uses the configured `review-fixer` subagent after explicit approval via the `task: ask` gate. Required equivalent CI supplies broad verification, or the full local gate runs once as fallback.

The retired ADR-0021 worker evidence contract is replaced by compact PR-body evidence: each active behavioral criterion carries focused passing proof, non-behavior criteria carry a narrow rationale, bug fixes add defect-specific RED, extra proof is required only when the ticket names it, and a retired criterion ID is never accepted as active evidence.

ADR-0031 retires generic conditional evidence profiles. Browser, security, operability, migration, compatibility, and performance proof is ordinary criterion evidence only when the ticket's acceptance criteria, risk, constraints, or smallest verification names it.

Technical depth lives in the leaf documents named by each line.
