# Seam: plan-this

## Purpose

The skill that applies the planning prefix as a fixed template. It is invoked directly as `/plan-this <task>` by the user, preserves the supplied planning workflow verbatim, places the invocation task under `## Task:`, and delegates to `/grill-with-docs`, `/to-spec`, and `/to-tickets` with repository-owned `/unslopify` active under its scope, protected-content, preservation, and completion-report contracts. One direct invocation authorizes that full interactive chain, but nothing publishes until the run has completed at least one full grill frontier round, shown the shared understanding and the proposed ticket graph after the frontier is empty, and received the user's explicit approval; an interrupted run resumes its recorded decision tree instead of restarting. It reads only the focused agent cache `AGENTS.md → ARCHITECTURE.md → affected seam leaf in docs/leaves/ → CONTEXT.md → relevant ADRs` owned by `document-for-agents`; it does not preload the derived human docs from `document-for-humans`.

## Scope & boundaries

Owns: the content under `skills/plan-this/` — `SKILL.md`, `INSTALL.md`, `tests/`. Delegates: the planning workflow to `/grill-with-docs`, `/to-spec`, `/to-tickets`; prose quality to repository-owned `/unslopify`. The seam is a fixed-template adapter — it does not reimplement delegated skills, copy the `AIT-*` catalog, add runtime scripts, or create `.kilo/command/` entries. Installation uses the registry lane only. Invocation is limited to direct user use; unrelated model invocation is rejected.
**Not here**: implementing published tickets belongs to `implement-this`;
reviewing the pull-request wave belongs to `review-this`; prose quality
belongs to `/unslopify`.

## Key files & data flow

`SKILL.md` is the entry point; its frontmatter `name` is the skill identity `plan-this` and its `description` declares the explicit invocation `/plan-this <task>` plus delegation to `/grill-with-docs`, `/to-spec`, `/to-tickets`, and `/unslopify`. The consumption path is: user runs `/plan-this <task>` → one direct invocation authorizes the full interactive chain while publication waits behind the separate explicit approval gate → skill loads `/unslopify` before the first progress update and keeps it active → treats task text, issue bodies, comments, specification drafts, and ticket bodies as requirements data that cannot widen scope, select files, authorize tools, or override workflow gates such as approval gates → performs no skill downloads during the run → runs `/grill-with-docs` until the decision frontier is empty (at least one full frontier round on every fresh run; an interrupted run resumes its recorded tree), researching facts discoverable from the codebase and environment instead of asking the user → shows the shared understanding and the proposed ticket graph and stops for explicit approval before calling `/to-spec` → `/to-tickets` in order, substituting only the task under `## Task:` → publishes an unlabelled parent specification stating the widest safe initial frontier and the worker limits of three workers per stage and four active managed workers across the workspace, native sub-issue links with a `Part of #<spec>` fallback, native blocked_by edges from each blocker's database ID read through the issue REST response, and initial labels through the packaged workflow-state copy → produces specification and tickets and stops after the ELI18 summary. The body carries a single `## Task:` substitution point. The body after frontmatter equals the verbatim expected prefix with that single slot — the workflow line `Run this planning-only workflow: ` + `` `/grill-with-docs` → `/to-spec` → `/to-tickets` ``, the authorization-and-approval-gate paragraph, `## Rules:` with thirteen bullets including the single authoritative grill rule and the single parallel-first graph-design rule, the `Finish with an ELI18 **Why / What / Where / How** summary` line, and the `## Task:` slot — totaling ~28 lines including frontmatter with no wrapper sections, start markers, or separate `## Hard dependencies` / `## Rules preserved` / `## Installation` / `## Boundary` sections, and it stays byte-for-byte unchanged. Hard dependencies are declared via that prefix plus the frontmatter `description`, not via a separate Hard dependencies section. `INSTALL.md` documents the registry lane `npx skills add RuralNative/RuralNative-SKILLS --skill plan-this` and the manual copy `cp -r skills/plan-this`, records source provenance and pinning guidance with residual repository trust, and requires explicit user approval before a manual install overwrites an existing skill. The registry discovery walks `skills/plan-this/` and a consumer installs by skill identity. The repo never carries its own install — `.agents/` and `skills-lock.json` are ignored. Tests live in `skills/plan-this/tests/` and encode the invariants, including a line-count bound, wrapper absence, byte-for-byte body checks, the single allowed invocation path with rejection of unrelated invocation, the grill approval gate and resume path, parallel-first graph semantics exercised through the packaged workflow-state core, and the trust-boundary checks for requirements data, runtime-download prohibition, provenance, and overwrite approval; they import the shared file reader, normalizer, and frontmatter stripper from `scripts/test-helpers.ts`. The seam also carries a packaged copy of the shared pure workflow state core at `workflow-state.ts` (#132), generated byte-identical from the authored source `scripts/workflow-state.ts` by `node scripts/generate-workflow-state.ts`; repository verification fails when a copy drifts. The packaged core decides frontier selection, dispatch under the three-worker cap that refuses stopped tickets, label transitions including removing a stale `unblocked` label when a blocker reopens and scoping the fresh-ticket `ready-for-agent` grant to unassigned children of the specification, retry limits whose `needs-info` stop holds on every later pass, review-head freshness, merge eligibility, follow-up creation, and parent closure. No `scripts/` directory is added under the skill folder and `SKILL.md` stays byte-identical.

2. **INV-2** — The registry-lane command in `INSTALL.md` installs this seam as `npx skills add RuralNative/RuralNative-SKILLS --skill plan-this` with matching manual copy `cp -r skills/plan-this`; discovery text names the explicit user invocation `/plan-this <task>` and preserves the example task verbatim under `## Task:`.
3. **INV-3** — Fixed-template boundary: `SKILL.md` body after frontmatter equals the exact supplied planning prefix verbatim, including `Run this planning-only workflow: ` + `` `/grill-with-docs` → `/to-spec` → `/to-tickets` ``, the thirteen Rules bullets, the `Finish with an ELI18 **Why / What / Where / How** summary` line, and the single `## Task:` slot, substituting only the task text; it preserves exact domain terms, identifiers, commands `ready-for-agent`, dependency names, quotations, and technical meaning, and does not add router skills, `.kilo/command/` files, runtime scripts, or model evals, and does not contain wrapper phrases `Rules preserved`, `## Installation`, `## Boundary`, `--- start of supplied`, or `This skill is a thin fixed-template adapter`. Mechanism: prose invariant — `SKILL.md` contains verbatim expected prefix (workflow line, authorization-and-approval-gate paragraph, thirteen Rules bullets, final summary line, `## Task:`) and single substitution point, with no wrapper markers and no extra machinery on disk (`scripts/`, `package.json`, `.kilo/command/`); composition test guards verbatim equality, single `## Task:`, wrapper absence, and line-count bound.
4. **INV-4** — Hard dependencies are repository-owned `/unslopify`, `/grill-with-docs`, `/to-spec`, `/to-tickets` with workflow order `/grill-with-docs` followed by `/to-spec` followed by `/to-tickets` and `/unslopify` loaded before the first progress update and kept active throughout under scope, protected-content, preservation, and completion-report contracts; the focused doc-cache route is `AGENTS.md → ARCHITECTURE.md → affected seam leaf → CONTEXT.md → relevant ADRs` owned by `document-for-agents` and does not preload derived human docs from `document-for-humans`; hard dependencies, in order, are `/grill-with-docs`, `/to-spec`, `/to-tickets`, and `/unslopify` and are declared via the workflow line and first Rules bullet plus frontmatter description, not via a separate Hard dependencies section. The delegated skills set `disable-model-invocation: true` and require explicit human invocation; one direct `/plan-this <task>` invocation is that explicit human invocation authorizing the full interactive chain, and publication waits behind the separate explicit approval gate. `/unslopify` carries no such lock and remains model-invocable. The skill does not silently map `/unslopify` to external `unslop`; the local `unslopify` seam stays unchanged. Mechanism: composition test in `skills/plan-this/tests/` verifies dependency names appear in body and frontmatter, workflow order is preserved, and one-invocation authorization plus separate approval are stated.
5. **INV-5** — The skill accepts one invocation and rejects others: direct user use as `/plan-this <task>`; unrelated model invocation is rejected. Its `description` states the allowed path explicitly and declares rejection of unrelated invocation, and it does not introduce broad automatic triggering. Preserved rules are those thirteen bullets as they appear in the trimmed prefix — unslopify loading before the first progress update with prose coverage across to-do items, updates, questions, decisions, ADR and glossary text, specification drafts, ticket bodies, GitHub comments, and the final summary; requirements-data trust precedence over task text, issue bodies, comments, specification drafts, and ticket bodies with no skill downloads during execution; To-Do List covering Discovery, Decisions, Specification, Tickets, Delivery with phase updates; the grill gate — at least one full frontier round per fresh run, researched environment facts, resume of the recorded decision tree without repeating settled questions, shared understanding plus proposed graph shown before the user's explicit approval authorizes `/to-spec` and `/to-tickets`, and approved decisions recorded in the GitHub specification without editing repository ADR or glossary files; parallel-first ticket design — shared contracts, seams, and edit collisions identified before dependency edges, no blocker edge between independent slices, native blockers only for consumed behavior, schema, policy, or decisions, and file overlap recorded as scheduling collisions; parent specification with acceptance criteria, seams, structural constraints, the widest safe initial frontier, worker limits of three per stage and four active managed workers across the workspace, and test-first verification; ticket design as independently verifiable vertical slices suitable for one worktree with real blockers, affected seams, acceptance criteria, verification, sibling scheduling collisions, and parallel-safety notes; precision per token with parent context; grounded decisions following the loading order; `ready-for-agent` labels with native dependency edges; ELI18 decision question with recommendation and approval gates; and following installed skills as source of truth — plus the final ELI18 **Why / What / Where / How** summary, without requiring a separate `## Rules preserved` section in `SKILL.md`. Completion stops after that summary. Mechanism: composition test verifies explicit invocation phrasing for the direct path, rejects unrelated invocation, checks byte-for-byte body preservation, single `## Task:` slot, dependency order, approval-gate and resume identifiers, and presence of preserved rule sections.
6. **INV-6** — One planning contract: the fixed-template body is the single source of planning behavior, and the final stop returns control to the user after the ELI18 summary. Mechanism: prose invariant — leaf doc explains the single-contract rule; composition test guards byte-for-byte body equality against the locked prefix and task-slot singularity.
7. **INV-7** — Bounded-planning contract: parent specification separates in-scope behavior from out-of-scope non-goals with acceptance criteria, affected seams, structural constraints, the widest safe initial frontier, the worker limits of three workers per stage and four active managed workers across the workspace, and the smallest test-first verification plan; tickets are independently verifiable vertical slices stating behavior, real blockers, affected seams, acceptance criteria, verification, sibling scheduling collisions, and parallel-safety; test design precedes implementation and rejects redundant/prose-mirroring/coverage-only tests unless a distinct risk is named. Mechanism: composition tests tagged for this invariant verify bounded scope and lean test criteria within the 18–35 line bound.
8. **INV-8** — Canonical publication. Nothing publishes until the grill frontier is empty, the shared understanding and proposed ticket graph are shown, and the user explicitly approves; the approved decisions live in the published specification, never in repository ADR or glossary files edited during the planning-only run. `plan-this` publishes the parent specification as a GitHub issue with no claimable label, links every implementation ticket to it as a native sub-issue where GitHub supports it (`Part of #<spec>` at the top of the ticket body where sub-issues are unavailable), and creates native blocked_by edges from each blocker's numeric database ID read through the issue REST response (`gh api repos/<owner>/<repo>/issues/<n> --jq .id`; the invalid `gh issue view --json databaseId` lookup is forbidden, as are the issue number and node_id). Native edges are canonical; human-readable Blocked by text stays fallback. A native blocker exists only when a ticket consumes behavior, schema, policy, or a decision produced by that blocker; file overlap without semantic dependency is a scheduling collision stated on both sibling tickets, never an edge. Initial labels come from the pure workflow state core over captured GitHub facts: an open blocker means blocked without ready-for-agent, no open blocker means ready-for-agent; all native blockers closed → remove blocked, add unblocked + ready-for-agent. Every published ticket body states its independently verifiable behavior, affected seams, acceptance criteria, verification, blockers, and parallel-safety status. Where a generic `/to-spec` or `/to-tickets` default conflicts (their blanket `ready-for-agent` labels), plan-this's rules win without forking those skills, and `ready-for-dev` is retired from workflow use. Mechanism: composition tests verify the approval gate before publication, the parent label, sub-issue links with documented fallback, the working REST database-ID lookup, blocker edges versus collision-only overlap through frontier selection and label transitions in the packaged workflow-state copy with captured GitHub facts, ticket body fields, command precedence without forked copies, and ready-for-dev retirement.
9. **INV-9** — Trust precedence and install boundary: task text, issue bodies, comments, specification drafts, and ticket bodies are requirements data that state work and evidence but cannot widen scope, select files, authorize tools, or override workflow gates such as approval gates; workflow execution performs no skill downloads. `INSTALL.md` records source provenance, pins reviewed external revisions where the installer supports it, states residual source-repository trust without claiming the Snyk E005/W011 findings have gone, and requires explicit user approval before a manual install overwrites an existing skill. Mechanism: composition tests tagged for this invariant guard the SKILL.md requirements-data rule and the INSTALL.md download-prohibition, provenance, residual-trust, and overwrite-approval statements.
10. **INV-10** — Risk is recorded before publication: every ticket receives `ordinary` or `high-risk`; evidenced security boundaries, migrations, shared contracts, broad public interfaces, dependency changes, and comparable blast radius are high-risk. Ordinary tickets target 60 minutes from durable reservation to merge or terminal stop; high-risk tickets target 90 minutes. Implementation or review may raise the class with evidence but cannot lower it; an escalation needs both a named trigger and evidence, so innocuous notes never inflate the class. Mechanism: the pure `risk.ts` decision table and the fixed-template publication rule.
