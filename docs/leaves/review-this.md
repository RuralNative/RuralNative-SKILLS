# Seam: review-this

## Purpose

The skill that owns one pull-request review wave through merge, dependent promotion, and final closure. It accepts `/review-this <target>` for a parent specification, child issue, pull request, or full URL, resolves the target before any worktree or GitHub write, discovers native child tickets and linked pull requests, reconciles Kilo cloud review with the local Standards and Spec review against each current head, routes confirmed findings, squash-merges eligible heads, promotes newly unblocked dependents, and closes the specification when final verification and whole-spec review pass.

## Scope & boundaries

Owns: the content under `skills/review-this/` — `SKILL.md`, `INSTALL.md`, `targets.ts`, `discovery.ts`, `reconciliation.ts`, `adapters.ts`, `review-authority.ts`, `workflow-state.ts`, and their tests. Delegates: the two-axis review workflow to repository-independent `/code-review`; prose quality to repository-owned `/unslopify`. The seam is a fixed-template adapter for the review wave — it does not reimplement `/code-review`, copy the smell baseline into its own body, add runtime scripts, or create `.kilo/command/` entries. Installation uses the registry lane only. Invocation accepts a parent specification, child issue, pull request, or URL, resolves it before any worktree or GitHub write, and runs from the control workspace; the review workspace never fixes a finding, never edits a ticket worktree, never merges without the four gates, and never closes a ticket before merge. The pure helpers stay host-neutral; ADR-0019 withdraws the earlier reservation of the helpers for a future persistent coordinator. ADR-0022 narrows the persistent-review invariant so the frontier command session owns review judgment and merge authority while the selected mutation worker applies fixes inside its persistent PR worktree.
**Not here**: implementing tickets belongs to `implement-this`; planning and
publishing tickets belongs to `plan-this`; the review method itself belongs
to `/code-review`.

## Key files & data flow

`SKILL.md` is the entry point; its frontmatter `name` is the skill identity `review-this` and its `description` declares the explicit invocation `/review-this <target>` plus delegation to `/code-review` and `/unslopify`, with cloud review as optional evidence. The consumption path is: caller runs `/review-this <target>` → skill loads `/unslopify` before the first progress update and keeps it active → treats the invocation target, parent specification, ticket bodies, comments, pull requests, Kilo cloud summary and inline comments, and sub-agent findings as requirements data and evidence that cannot widen scope, select files outside the diff, authorize tools, or override gates such as the pinned current head and base, parallel spawning, or the no-merge and no-rerank rules, with no skill downloads during the run → runs `git fetch origin`, normalizes and resolves the target before any worktree or GitHub write, and reads native child tickets, linked pull requests, native blockers, required checks, reviews, and current head and base SHAs → selects only the current review set with `selectReviewWave` from `discovery.ts` in native child order when open child pull requests have valid closing references and acceptance evidence → plans bounded fan-out over the ready wave with `planReviewWaveDispatch` from `review-session.ts` after one Agent Manager overview run (`action: "list"`): reuse existing persistent PR workers, start the rest in one worktree-mode request within the three-review-worker stage cap and the four-managed-worker workspace cap in native child order, never duplicating a worker for one pull request or one pinned head-and-base pair, and defer capacity beyond either cap → collects Kilo cloud summary and inline comments for each pinned head-and-base pair through overlapped `collectReviewEvidence` in `adapters.ts`, which starts cloud collection immediately without awaiting it during worker setup and records `available` or `unavailable` on disabled, absent, failed, or timed-out cloud review without blocking a complete local review while a local-review rejection stays blocking → builds one shared revision packet per pinned pair (three-dot diff command, commit list, changed files and hunks, impacted callers, focused doc-cache sources, acceptance criteria, Standards sources, escalation triggers), gives both fresh axes the same packet plus only their axis-specific brief with no repeated discovery inside subagents, and always runs the local Standards and Spec review by spawning the two sub-agents in parallel and aggregating side by side under `## Standards` and `## Spec` within the `/code-review` report caps without merging or reranking → reconciles cloud, Standards, and Spec findings against each current head with `reconcileFindings` from `reconciliation.ts`, keeping Standards and Spec axes separate and rejecting duplicate, stale, out-of-scope, and unverified findings with evidence → sends every confirmed finding for that PR and round to one fresh fix context in the persistent PR worktree, batches safe advisories with blocking fixes, and defers advisory-only findings → invalidates previous checks and review when a pushed fix changes the head or base revision and requires a new current-head verdict via `reviewIsFresh` → checks merge eligibility with `isMergeEligible` from the packaged `workflow-state.ts` (green required checks, resolved confirmed findings, clean local review, unchanged reviewed head and base, published trusted summary, and verified inline findings) and squash-merges eligible pull requests whose bodies carry `Closes #<ticket>` → uses `promotionAfterClosure` to update only dependents whose final open native blocker closed (add `unblocked` plus `ready-for-agent`, remove `blocked`) and tells the user to run `implement-this #<spec>` when more tickets become ready → when every child ticket closes, checks updated `main` with `npm run verify` and a whole-spec Standards and Spec review, repairs a failed final gate with one available fix round followed by delta or escalated rereview, creates the smallest independently verifiable native child ticket for a confirmed integration defect while keeping the parent open (`followUpRequired`), and closes the parent only when `parentClosureReady` passes. Each active pull request proceeds independently through local review, reconciliation, publication, fixes, and merge while another waits on cloud review or CI, and the upserted trusted summary carries the phase timings (`packetBuildMs`, `cloudMs`, `localReviewMs`, `reviewCriticalPathMs`, `reconcileMs`, `ciWaitMs`, plus the wave facts `activeReviewWorkers` and `deferredByCapacity`) as bookkeeping that is never merge evidence and removes no gate. The body carries a single `## Spec` substitution slot hosting only the parent specification text.

The skill packages a runtime copy of the pure workflow state core at `workflow-state.ts` (#132): frontier selection, dispatch validation with the three-worker cap, label decisions, one-retry recovery with the `needs-info` stop, head freshness, merge eligibility, follow-up creation, and parent completion decisions. The authored source is `scripts/workflow-state.ts`; running `node scripts/generate-workflow-state.ts` regenerates byte-identical copies into all three workflow skills, and repository verification fails when a copy drifts.

`discovery.ts` selects the review wave from observed ticket and pull-request facts. `targets.ts` resolves one invocation target — parent specification, child issue, pull request, bare number, hash number, or URL — into a plan of facts and decisions before any write: reference normalization, object-type resolution in the shared issue and pull-request number space, closing-reference derivation, readiness blockers, Standards-only handling for spec-less pull requests, and named diagnostic states; it imports `selectReviewWave` for parent mode. `reconciliation.ts` reconciles findings across sources while keeping Standards and Spec axes separate, emitting the four rejection reasons plus the incomplete reason with evidence and preserving the optional `ticket` on each finding; a candidate with a missing category or severity is rejected as incomplete and never defaults to a blocking correctness finding, and Standards and Spec keep axis identity during deduplication. `adapters.ts` declares the host capability contracts — `GitHubAdapter`, `CloudAdapter`, `LocalReviewAdapter`, `MergeAdapter`, `VerificationAdapter` — with `collectCloudReview` wrapping adapter failures as `unavailable`, `collectReviewEvidence` starting cloud and local collection together for one pinned pair (#170), `validateStandardsCategoryTransport` checking required Standards category statuses, and `fake*` helpers for tests that never call live cloud review, GitHub, or worker sessions. `review-authority.ts` (#173) carries the frontier/worker authority split: frontier-owned responsibilities, live-catalog execution-model resolution, mutation-worker boundaries, worker-failure budget, required Standards category transport, axis-preserving deduplication decisions, specialist routing, and specialist-evidence validation.

`review-session.ts` adds the #157 and #158 performance contract: one persistent PR worktree and worker automatically created via the `agent_manager` tool in worktree mode after the Agent Manager overview (`action: "list"`), fresh parallel initial agents and one fresh fix context per round inside that established worktree, strict category coverage, advisory batching and deferral, approved root-cause seam expansion, delta-versus-full escalation, final-verification repair, publication gates, and bounded operation counts. The persistent Agent Manager PR worker is created before any Standards, Spec, or fix `Task` subagents; `Task` cannot replace it and nested `Task` contexts are valid only inside the established worktree and run only after explicit user approval via the tracked `agent_manager: allow` and `task: ask` project permission gate, which never edits `.kilo/agent-manager.json`. Hosts that cannot provide the persistent worktree stop before a verdict. `planConflictResolution` models base movement against the bounded rounds at this layer too: a conflict-free base refresh reuses the verdict without consuming a fix round, resolving a real merge conflict consumes one bounded round and receives delta rereview, and a conflict at the round maximum stops. Scenario tests drive the operation counts through the clean, one-fix, two-fix, base-delta, conflict, and final-verification-repair paths. `planReviewWaveDispatch` (#170) plans bounded fan-out over the native-order wave from the observed PR worker facts, workspace slots, and the three-worker stage cap and four-worker workspace cap: reusable workers, one worktree-mode start per remaining ready PR, and capacity deferrals with reasons. Test-only fakes now live in `tests/fakes.ts`; production adapters contain host contracts only. A current PR head plus implementation evidence starts review immediately, and a missed SLO or failed summary publication never removes a review, verification, trust, or merge gate.

## Non-negotiables

1. **INV-1** — `SKILL.md` frontmatter `name` equals the folder name `review-this`. Mechanism: identity composition test and docs harness.
2. **INV-2** — `SKILL.md` frontmatter and `INSTALL.md` use the target form consistently. `INSTALL.md` uses `npx skills add RuralNative/RuralNative-SKILLS --skill review-this`, gives a matching manual copy, and documents the explicit invocation `/review-this <target>` plus verification via `/review-this #130`. Mechanism: composition test.
3. **INV-3** — Fixed-template boundary: `SKILL.md` body after frontmatter equals the verbatim expected prefix, including the workflow line `Review the parent specification's pull-request wave: `/code-review``, the `## Rules` bullets, and the single `## Spec` slot hosting only the parent specification text; it contains no wrapper phrases `Rules preserved`, `## Installation`, or `## Boundary`, adds no runtime scripts, no `package.json`, and no `.kilo/command/` files. Invocation resolves a parent specification, child issue, pull request, or URL before discovering native child tickets, linked pull requests, blockers, checks, reviews, and current head and base SHAs. The command selects only the current review set and runs once from the control workspace. Mechanism: composition test guards verbatim equality, single-slot substitution, wrapper absence, and discovery phrasing.
4. **INV-4** — Hard dependencies are `/code-review` and `/unslopify` in that order. `/unslopify` loads before the first progress update and stays active under its scope, protected-content, preservation, and completion-report contracts. `/code-review` carries no `disable-model-invocation` lock and remains model-invocable. The focused doc-cache route is `AGENTS.md → ARCHITECTURE.md → affected seam leaf → CONTEXT.md → relevant ADRs` and does not preload derived human docs from `document-for-humans`. Mechanism: composition test verifies dependency names and order appear in body and frontmatter.
5. **INV-5** — Target-resolution and discovery contract: `normalizeReference` and `resolveReviewTarget` from `targets.ts` normalize bare and hash references identically, accept full issue and pull-request URLs for the current repository, stop cross-repository targets before writes unless the user explicitly chose that repository, and resolve parent specifications, child issues, and pull requests into a plan carrying the exact pull-request set, the Spec availability, and auto-merge permission, with named diagnostic states (`malformed-reference`, `target-not-found`, `cross-repository-target`, `closed-pull-request`, `missing-pull-request`, `standalone-issue-without-pull-request`, `ambiguous-pull-requests`) and no review or fix worktree intent for an invalid or ambiguous target. `selectReviewWave` from `discovery.ts` then returns open child pull requests whose linked ticket matches their valid closing reference and whose current head and base SHAs are non-empty, in native child order, with posted implementation acceptance evidence, skipping an already-reviewed unchanged head-and-base pair while rediscovering pull requests created after invocation. A pull request without an originating specification produces a Standards-only plan that cannot auto-merge, and direct PR readiness also rejects a mismatched linked ticket. Readiness never comes from `ready-for-human`, which keeps its triage meaning. The helpers perform no network, GitHub, git, filesystem mutation, or worker-management calls. Mechanism: table-driven pure unit tests over `targets.ts` and `discovery.ts` with fakes only (#156).
6. **INV-6** — Cloud and local review contract: Kilo cloud summary and inline comments are collected for the current head when available via `collectCloudReview` from `adapters.ts`; cloud absence, failure, or timeout is recorded as `unavailable` (including adapter rejection via try/catch) and does not block a complete local review. The local Standards and Spec review always runs; cloud absence never blocks it, and cloud unavailability never cancels or skips the already-running local review. `collectReviewEvidence` (#170) starts cloud collection and local review together for one pinned head-and-base pair and awaits both only at that PR's reconciliation boundary; a local-review rejection is blocking, stale local revisions are rejected by name, and mismatched cloud revisions remain `unavailable`. Mechanism: adapter tests with `fakeCloudAdapter` for available, unavailable, and rejection-as-unavailable paths plus deferred-fake overlap tests proving both sources start before either resolves, and composition phrasing checks.
7. **INV-7** — Finding reconciliation: `reconcileFindings` from `reconciliation.ts` reconciles cloud, Standards, and Spec findings against each current head, keeping Standards and Spec axes separate. Duplicate, stale, out-of-scope, and unverified findings are rejected with evidence; a duplicate keeps the clearest evidence and counts once. The retained findings for one PR become one fresh fix batch in the persistent PR worktree, with safe advisories joining a blocking batch and advisory-only findings receiving a reasoned deferral. Mechanism: pure tests over `reconciliation.ts` and `review-session.ts`. (Amended by ADR-0019: confirmed findings apply in one fresh fix worktree per pull request and round instead of returning to the owning implementation worker, effective with #158.)
8. **INV-8** — Freshness and merge gates: a pushed fix invalidates previous checks and review for that pull request and requires a new current-head verdict via `reviewIsFresh`; merge requires green required checks, resolved confirmed findings, a clean local review, an unchanged reviewed head and base pair, a published trusted summary, verified inline findings, and a mergeable pull request via `isMergeEligible` from the packaged `workflow-state.ts`. The reviewer verifies every finding against the current head before publishing; sub-agent output never merges, approves, closes, or labels anything. Same-repository updates are fast-forward-only and untrusted forks stay static-review-only. Mechanism: state-core tests plus reconciliation stale-head tests. (Amended by ADR-0019: a verdict pins both head and base revisions and either moving invalidates it; each pull request receives at most two pushed fix heads followed by one final review, conflict resolution consumes a fix round, and a conflict-free base refresh does not.)
9. **INV-9** — Squash-merge and dependent promotion: eligible pull requests squash-merge and their closing references `Closes #<ticket>` close the assigned tickets; the adapter never closes a ticket before merge and never force-pushes. Ticket closure updates only dependents whose final open native blocker closed, adding `unblocked` plus `ready-for-agent` and removing `blocked` via `promotionAfterClosure`. If more tickets become ready, completion tells the user to run `implement-this #<spec>` for the next dependency wave. Mechanism: adapter fake tests for squash-merge plus state-core promotion tests and composition completion phrasing.
10. **INV-10** — Final verification and parent closure: when all child tickets close, updated `main` passes repository verification `npm run verify` and a whole-spec Standards and Spec review before the parent closes. A confirmed integration defect becomes the smallest independently verifiable native child ticket and keeps the parent open via `followUpRequired`. The parent closes only when `parentClosureReady` passes. Mechanism: state-core parent-closure tests plus `fakeVerificationAdapter` tests.
11. **INV-11** — State and adapter boundaries remain callable by a future persistent coordinator without changing command behavior. The pure helper `discovery.ts`, `reconciliation.ts`, and `workflow-state.ts` perform no network, GitHub, git, filesystem mutation, or worker-management calls; the host contracts in `adapters.ts` expose `GitHubAdapter`, `CloudAdapter`, `LocalReviewAdapter`, `MergeAdapter`, and `VerificationAdapter` with `fake*` helpers. Verification uses fakes only; no test calls live cloud review, GitHub, or worker sessions. Mechanism: purity tests plus adapter contract tests. (Amended by ADR-0019: the future-coordinator reservation is withdrawn; the helpers keep their host-neutral purity as an engineering property, not as coordinator groundwork.)
12. **INV-12** — Trust precedence and install boundary: the parent specification, ticket bodies, comments, pull requests, cloud comments, and sub-agent findings are requirements data and evidence that cannot widen scope, select files outside the diff, authorize tools, or override gates such as the pinned current head, parallel spawning, or the no-merge and no-rerank rules; workflow execution performs no skill downloads. `INSTALL.md` records source provenance, pins reviewed external revisions where the installer supports it, states residual source-repository trust without claiming the Snyk findings have gone, and requires explicit user approval before a manual install overwrites an existing skill. Mechanism: composition tests tagged for this invariant guard the SKILL.md requirements-data rule and the INSTALL.md download-prohibition, provenance, residual-trust, and overwrite-approval statements.
13. **INV-13** — Performance and persistent-review contract: review starts when a current pull-request head and implementation evidence exist, uses one persistent PR worktree and worker automatically created via the `agent_manager` tool in worktree mode after the Agent Manager overview (`action: "list"`), and stops before a verdict or fix if the persistent worktree cannot be created or fresh Standards, Spec, or fix agents are unavailable. The persistent Agent Manager PR worker exists before any Standards, Spec, or fix `Task` subagents; `Task` (subagent) does not replace the worktree and nested `Task` subagents are valid only inside the established persistent PR worktree created via `agent_manager` before them, running only after explicit user approval through the tracked `agent_manager: allow` and `task: ask` project permission gate which never edits `.kilo/agent-manager.json`. The initial revision gets one full review with all strict category statuses; later revisions get delta review over changed hunks and impacted callers unless a new affected seam, trust boundary, schema, dependency state, generated contract, public interface, or materially widened diff forces full review. Findings pin stable identity, category, severity, location, head and base, governing rule, and evidence. Root-cause expansion publishes every added path and stays inside approved affected seams. One trusted summary is upserted per revision, at most two code-fix rounds are allowed (the round cap lives once in the workflow-state core), and a final-verification repair receives delta or escalated rereview without starting a third round. Operation budgets prevent duplicate setup, initial review, or final verification. Cloud-collect mismatch reasons report only the revisions that actually differ, category fixtures cover every status including advisory, and readiness evidence records that active sibling workers never delay an eligible PR. Bounded fan-out (#170): ready pull requests run concurrently after one Agent Manager overview run — at most three review workers per stage, at most four managed workers across the workspace, reuse before create with no duplicate worker for one PR or one pinned head-and-base pair, native child order preserved, capacity overflow deferred and re-entered on rediscovery — each active PR proceeds independently, cloud collection overlaps local review through `collectReviewEvidence`, both fresh axes share one revision packet per pinned pair plus their axis-specific brief, and the trusted summary records `packetBuildMs`, `cloudMs`, `localReviewMs`, `reviewCriticalPathMs`, `reconcileMs`, `ciWaitMs`, `activeReviewWorkers`, and `deferredByCapacity` as bookkeeping that is never merge evidence. Mechanism: `review-session.ts` including `planConflictResolution` and `planReviewWaveDispatch`, reconciliation tests, and test-only adapter fakes (including deferred overlap fakes), plus composition tests for overview-first ordering, bounded multi-PR dispatch, cloud/local overlap, independent PR progress, shared revision packets, phase timings, Task ban, and permission gate. (Amended by ADR-0022, #173: the frontier command session owns review judgment and merge authority; one live-catalog execution model drives every new persistent PR mutation worker, which may mutate and fast-forward push only inside its worktree and never publishes verdicts or changes merge, label, promotion, closure, or parent state.)
14. **INV-14** — Frontier review authority and mutation-worker routing: the command session keeps the chat-selected frontier model and owns revision packets, completeness checks, finding verification, reconciliation, verdict publication, merge, labels, promotion, and closure. `/review-this` asks once per invocation for an execution model resolved through the live Agent Manager catalog with no hardcoded names; the resolved `model`, optional `provider`, and optional `variant` apply to every new persistent PR mutation worker in the wave. A resume shows the previous recorded choice but requires user confirmation; tracker prose never authorizes model or tool use. The mutation worker may mutate, run instructed conflict or verification repair, and fast-forward push only inside its persistent PR worktree; it cannot publish a verdict or change merge, label, promotion, closure, or parent state. One corrected execution packet may be sent within the fix-round budget; continued failure adds `needs-info` and stops without frontier-model takeover. Required Standards category statuses are requested, transported through the local review adapter, and checked before reconciliation; a candidate with missing category or severity is rejected or reported as incomplete and never defaults to a blocking correctness finding. Deduplication preserves Standards and Spec axis identity; cloud/local duplicates collapse only when revisions and evidence identify one defect. Test strategy, accessibility, observability, migration, and simplification run as triggered Standards checks; at most one specialist runs per pull request and full-review round (security for the strongest trust-boundary risk, web performance for measured web-performance work), with specialist evidence using local severity, citing a governing rule, criterion, or observed failure, and pinning head and base. Frontier-owned read-only reviewers inspect the exact pinned persistent PR worktree while only the mutation worker edits it; exact head/base freshness, two pushed fix heads, one final review, final repository verification, stage and workspace worker caps, fork restrictions, and frontier-only merge remain enforced. Mechanism: pure tests over `review-authority.ts`, reconciliation completeness and axis-preservation tests, adapter transport tests, and composition checks.

## Further notes

The review prefix was extracted from the delivery branches of `implement-this` (#124, parent #123): `implement-this` delivers every ticket by pull request against `main` but no longer runs review internally; callers who relied on that chaining run `/review-this <target>` explicitly. ADR-0006's task-scoped fixed-template exception extends to this seam per #123, ADR-0013 (now superseded by ADR-0014) recorded the decoupling into a wave owner, and ADR-0014 ships the contract where the review wave owns merge, promotion, final verification, and parent closure rather than a fixed-point diff report. The boundary: this seam hosts only the wave review invocation template — `implement-this` owns implementation and delivery and does not run review; `/code-review` owns the two-axis review workflow itself, `REVIEW.md` owns the shared policy.

ADR-0019 (2026-08-23, parent spec #152) amends this seam for #156, #157, and #158: review resolves bare and hash references identically before object resolution and accepts parent issues, child issues, pull requests, and URLs; #157 adds the persistent PR worktree, exact head-and-base verdict pinning, strict initial review, timing summary, and bounded operation contracts; #158 adds the fresh fix-context and delta-rereview execution. A verdict pins both head and base revisions; each pull request receives at most two pushed fix heads followed by one final review, resolving a code conflict consumes a fix round, and a conflict-free base refresh does not; `ready-for-human` keeps its triage meaning and stops being pull-request readiness. Review command sessions start independently of implementation, poll with increasing delays, checkpoint after 30 minutes without progress, and resume idempotently from GitHub. Target resolution shipped with #156: `targets.ts` owns reference normalization and object resolution, `discovery.ts` owns wave selection from closing-reference and acceptance-evidence facts, and both keep the shipped wording above in force for everything the later tickets have not yet changed.

ADR-0022 (2026-08-28, parent spec #171, ticket #173) narrows the persistent-review invariant and adds the frontier review authority invariant: the frontier command session owns review judgment, revision packets, completeness, finding verification, reconciliation, verdict publication, merge, labels, promotion, and closure; one live-catalog execution model applies to every new persistent PR mutation worker, which may mutate, repair, and fast-forward push only inside its worktree; required Standards category statuses are transported and checked before reconciliation, missing category or severity is never a blocking correctness finding, and deduplication preserves axis identity; triggered Standards checks and at most one specialist per full-review round are added inside the Standards axis. Issue #170 stays open until this ticket publishes preservation evidence for bounded wave fan-out, shared revision packets, cloud/local overlap, independent PR progress, and timing records.
