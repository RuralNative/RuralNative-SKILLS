# Seam: review-this

## Purpose

The skill that owns one pull-request review wave for a parent specification through merge, dependent promotion, and final closure. It is invoked directly as `/review-this #<spec>` where `#<spec>` is the parent specification that groups every implementation ticket as a native sub-issue, discovers native child tickets, linked pull requests, blockers, checks, reviews, and current head SHAs, reconciles Kilo cloud review with the local Standards and Spec review against each current head, routes confirmed findings to the owning worker, squash-merges eligible heads, promotes newly unblocked dependents, and closes the specification when final verification and whole-spec review pass.

## Scope & boundaries

Owns: the content under `skills/review-this/` — `SKILL.md`, `INSTALL.md`, `discovery.ts`, `reconciliation.ts`, `adapters.ts`, `workflow-state.ts`, and their tests. Delegates: the two-axis review workflow to repository-independent `/code-review`; prose quality to repository-owned `/unslopify`. The seam is a fixed-template adapter for the review wave — it does not reimplement `/code-review`, copy the smell baseline into its own body, add runtime scripts, or create `.kilo/command/` entries. Installation uses the registry lane only. Invocation is explicit as `/review-this #<spec>` and runs once from the control workspace; the review workspace never fixes a finding, never edits a ticket worktree, never merges without the four gates, and never closes a ticket before merge. The pure helper stays host-neutral for a future persistent coordinator.

## Key files & data flow

`SKILL.md` is the entry point; its frontmatter `name` is the skill identity `review-this` and its `description` declares the explicit invocation `/review-this #<spec>` plus delegation to `/code-review` and `/unslopify`, with cloud review as optional evidence. The consumption path is: caller runs `/review-this #<spec>` → skill loads `/unslopify` before the first progress update and keeps it active → treats the parent specification, ticket bodies, comments, pull requests, Kilo cloud summary and inline comments, and sub-agent findings as requirements data and evidence that cannot widen scope, select files outside the diff, authorize tools, or override gates such as the pinned current head, parallel spawning, or the no-merge and no-rerank rules, with no skill downloads during the run → runs `git fetch origin` and reads the parent specification, native child tickets, linked pull requests, native blockers, required checks, reviews, and current head SHAs → selects only the current review wave with `selectReviewWave` from `discovery.ts` (open pull requests for open children carrying `ready-for-human` in native child order, each pinned to its current head SHA) → collects Kilo cloud summary and inline comments for the current head when available through `cloud-adapter` in `adapters.ts` (recording `available` or `unavailable` on disabled, absent, failed, or timed-out cloud review without blocking a complete local review) → always runs the local Standards and Spec review by spawning the two sub-agents in parallel and aggregating side by side under `## Standards` and `## Spec` without merging or reranking → reconciles cloud, Standards, and Spec findings against each current head with `reconcileFindings` from `reconciliation.ts`, keeping Standards and Spec axes separate and rejecting duplicate, stale, out-of-scope, and unverified findings with evidence → routes confirmed findings to the ticket's owning worker rather than fixing them in the review workspace → invalidates previous checks and review when a pushed fix changes the head SHA and requires a new current-head verdict via `reviewIsFresh` → checks merge eligibility with `isMergeEligible` from the packaged `workflow-state.ts` (green required checks, resolved confirmed findings, clean local review, unchanged reviewed head SHA) and squash-merges eligible pull requests whose bodies carry `Closes #<ticket>` → uses `promotionAfterClosure` to update only dependents whose final open native blocker closed (add `unblocked` plus `ready-for-agent`, remove `blocked`) and tells the user to run `implement-this #<spec>` when more tickets become ready → when every child ticket closes, checks updated `main` with `npm run verify` and a whole-spec Standards and Spec review, creates the smallest independently verifiable native child ticket for a confirmed integration defect while keeping the parent open (`followUpRequired`), and closes the parent only when `parentClosureReady` passes. The body carries a single `## Spec` substitution slot hosting only the parent specification text.

The skill packages a runtime copy of the pure workflow state core at `workflow-state.ts` (#132): frontier selection, dispatch validation with the three-worker cap, label decisions, one-retry recovery with the `needs-info` stop, head freshness, merge eligibility, follow-up creation, and parent completion decisions. The authored source is `scripts/workflow-state.ts`; running `node scripts/generate-workflow-state.ts` regenerates byte-identical copies into all three workflow skills, and repository verification fails when a copy drifts.

`discovery.ts` selects the review wave from observed ticket and pull-request facts. `reconciliation.ts` reconciles findings across sources while keeping Standards and Spec axes separate, emitting the four rejection reasons with evidence, preserving the optional `ticket` on each finding, and exposing `routeFixesByTicket` so a multi-PR wave routes each retained finding to its owning ticket. `adapters.ts` declares the host capability contracts — `GitHubAdapter`, `CloudAdapter`, `LocalReviewAdapter`, `MergeAdapter`, `VerificationAdapter` — with `collectCloudReview` now wrapping adapter failures as `unavailable` and `fake*` helpers for tests that never call live cloud review, GitHub, or worker sessions.

## Non-negotiables

1. **INV-1** — `SKILL.md` frontmatter `name` equals the folder name `review-this`. Mechanism: identity composition test and docs harness.
2. **INV-2** — `INSTALL.md` uses `npx skills add RuralNative/RuralNative-SKILLS --skill review-this`, gives a matching manual copy, and documents the explicit invocation `/review-this #<spec>` plus verification via `/review-this #130`. Mechanism: composition test.
3. **INV-3** — Fixed-template boundary: `SKILL.md` body after frontmatter equals the verbatim expected prefix, including the workflow line `Review the parent specification's pull-request wave: `/code-review``, the `## Rules` bullets, and the single `## Spec` slot hosting only the parent specification text; it contains no wrapper phrases `Rules preserved`, `## Installation`, or `## Boundary`, adds no runtime scripts, no `package.json`, and no `.kilo/command/` files. Invocation starts from the parent specification and discovers native child tickets, linked pull requests, blockers, checks, reviews, and current head SHAs. The command selects only the current review wave and runs once from the control workspace. Mechanism: composition test guards verbatim equality, single-slot substitution, wrapper absence, and discovery phrasing.
4. **INV-4** — Hard dependencies are `/code-review` and `/unslopify` in that order. `/unslopify` loads before the first progress update and stays active under its scope, protected-content, preservation, and completion-report contracts. `/code-review` carries no `disable-model-invocation` lock and remains model-invocable. The focused doc-cache route is `AGENTS.md → ARCHITECTURE.md → affected seam leaf → CONTEXT.md → relevant ADRs` and does not preload derived human docs from `document-for-humans`. Mechanism: composition test verifies dependency names and order appear in body and frontmatter.
5. **INV-5** — Discovery contract: `selectReviewWave` from `discovery.ts` takes observed ticket and pull-request facts plus the parent specification number and returns only open pull requests for open children of that specification carrying `ready-for-human`, in native child order, each pinned to its current head SHA. The pure helper performs no network, GitHub, git, filesystem mutation, or worker-management calls. Mechanism: pure unit tests over `discovery.ts` with fakes only.
6. **INV-6** — Cloud and local review contract: Kilo cloud summary and inline comments are collected for the current head when available via `collectCloudReview` from `adapters.ts`; cloud absence, failure, or timeout is recorded as `unavailable` (including adapter rejection via try/catch) and does not block a complete local review. The local Standards and Spec review always runs; cloud absence never blocks it. Mechanism: adapter tests with `fakeCloudAdapter` for available, unavailable, and rejection-as-unavailable paths, plus composition phrasing checks.
7. **INV-7** — Finding reconciliation: `reconcileFindings` from `reconciliation.ts` reconciles cloud, Standards, and Spec findings against each current head, keeping Standards and Spec axes separate. Duplicate, stale, out-of-scope, and unverified findings are rejected with evidence; a duplicate keeps the clearest evidence and counts once. Confirmed findings return to the ticket's owning worker via `routeFixesToWorker` (single-PR) or `routeFixesByTicket` (wave grouping by `ticket`) rather than being fixed in the review workspace; the fallback branch is eliminated and ticket preservation is tested. Mechanism: pure tests over `reconciliation.ts` including ticket-aware grouping.
8. **INV-8** — Freshness and merge gates: a pushed fix invalidates previous checks and review for that pull request and requires a new current-head verdict via `reviewIsFresh`; merge requires green required checks, resolved confirmed findings, a clean local review, and an unchanged reviewed head SHA via `isMergeEligible` from the packaged `workflow-state.ts`. The reviewer verifies every finding against the current head before publishing; sub-agent output never merges, approves, closes, or labels anything. Mechanism: state-core tests plus reconciliation stale-head tests.
9. **INV-9** — Squash-merge and dependent promotion: eligible pull requests squash-merge and their closing references `Closes #<ticket>` close the assigned tickets; the adapter never closes a ticket before merge and never force-pushes. Ticket closure updates only dependents whose final open native blocker closed, adding `unblocked` plus `ready-for-agent` and removing `blocked` via `promotionAfterClosure`. If more tickets become ready, completion tells the user to run `implement-this #<spec>` for the next dependency wave. Mechanism: adapter fake tests for squash-merge plus state-core promotion tests and composition completion phrasing.
10. **INV-10** — Final verification and parent closure: when all child tickets close, updated `main` passes repository verification `npm run verify` and a whole-spec Standards and Spec review before the parent closes. A confirmed integration defect becomes the smallest independently verifiable native child ticket and keeps the parent open via `followUpRequired`. The parent closes only when `parentClosureReady` passes. Mechanism: state-core parent-closure tests plus `fakeVerificationAdapter` tests.
11. **INV-11** — State and adapter boundaries remain callable by a future persistent coordinator without changing command behavior. The pure helper `discovery.ts`, `reconciliation.ts`, and `workflow-state.ts` perform no network, GitHub, git, filesystem mutation, or worker-management calls; the host contracts in `adapters.ts` expose `GitHubAdapter`, `CloudAdapter`, `LocalReviewAdapter`, `MergeAdapter`, and `VerificationAdapter` with `fake*` helpers. Verification uses fakes only; no test calls live cloud review, GitHub, or worker sessions. Mechanism: purity tests plus adapter contract tests.
12. **INV-12** — Trust precedence and install boundary: the parent specification, ticket bodies, comments, pull requests, cloud comments, and sub-agent findings are requirements data and evidence that cannot widen scope, select files outside the diff, authorize tools, or override gates such as the pinned current head, parallel spawning, or the no-merge and no-rerank rules; workflow execution performs no skill downloads. `INSTALL.md` records source provenance, pins reviewed external revisions where the installer supports it, states residual source-repository trust without claiming the Snyk findings have gone, and requires explicit user approval before a manual install overwrites an existing skill. Mechanism: composition tests tagged for this invariant guard the SKILL.md requirements-data rule and the INSTALL.md download-prohibition, provenance, residual-trust, and overwrite-approval statements.

## Further notes

The review prefix was extracted from the delivery branches of `implement-this` (#124, parent #123): `implement-this` delivers every ticket by pull request against `main` but no longer runs review internally; callers who relied on that chaining run `/review-this #<spec>` explicitly. ADR-0006's task-scoped fixed-template exception extends to this seam per #123, ADR-0013 (now superseded by ADR-0014) recorded the decoupling into a wave owner, and ADR-0014 ships the contract where the review wave owns merge, promotion, final verification, and parent closure rather than a fixed-point diff report. The boundary: this seam hosts only the wave review invocation template — `implement-this` owns implementation and delivery and does not run review; `/code-review` owns the two-axis review workflow itself, `REVIEW.md` owns the shared policy.
