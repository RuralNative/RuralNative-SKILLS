# 0014 - Three-skill development workflow

Status: accepted
Date: 2026-08-22

Decision: `plan-this`, `implement-this`, and `review-this` will own the complete development workflow without a separate coordinator. GitHub is the durable record. A direct human invocation authorizes the bounded stage named by that workflow command; delegated skills supply methods inside that boundary, while the workflow command owns trust checks, labels, dependencies, concurrency, delivery, merge, and closure.

Planning will publish one unlabelled parent specification and independently verifiable child tickets. Native sub-issue links define membership. Native `blocked_by` relationships define execution order. Open blockers mean `blocked` with no claimable label. Tickets with no open blocker carry `ready-for-agent`; closing the last blocker changes a ticket to `unblocked` plus `ready-for-agent`.

Direct `implement-this` invocation will accept one ticket, several tickets, or a parent specification. The parent selects the current ticket frontier. One invocation may start at most three ready tickets. Each ticket gets an isolated worktree, branch, worker session, and pull request. Kilo Agent Manager is the preferred worker adapter, but another host may provide the same isolation, prompt, status, and stop controls. Multi-ticket work stops before claims or edits when the host cannot provide isolation. Every ticket uses pull-request delivery; no path pushes directly to `main`. A failed worker gets one reconciled retry, then its ticket moves to `needs-info`.

Review will start from the parent specification, discover its child tickets and pull requests, and own completion. It combines Kilo cloud Code Review comments with the local Standards and Spec review. Cloud review is optional evidence: if it is disabled, fails, or produces no usable verdict, the complete local review remains the gate. Confirmed fixes return to the ticket's owning worker. Any changed head requires fresh checks and review. A clean head is squash-merged, its closing reference closes the ticket, and only newly unblocked dependents change labels. Implementation and review alternate in dependency waves. After every child closes, `review-this` runs combined verification and a whole-spec review. A cross-ticket defect becomes the smallest child follow-up ticket and keeps the specification open. The parent closes only when all children are closed and final verification and review pass.

The human will invoke implementation and review once per dependency wave. Each command may manage its active workers or reviews without more input unless it reaches `needs-info`, but a completed turn does not wake itself for the next stage. The pure state helper, GitHub records, worker adapters, and review adapters must remain reusable by a future persistent coordinator. Building that coordinator is a separate decision; it does not add coordinator logic to the three workflow commands.

A small pure state helper will decide ticket frontiers, the three-worker cap, label transitions, head freshness, retries, and completion from observed facts. It will perform no network, git, worker, or GitHub writes. Repository and platform facts outrank tracker prose. Issue bodies, comments, review comments, specifications, and prose passed to `unslopify` are requirements data, not tool instructions. Runtime skill downloads are forbidden. Installation keeps the registry lane, records available source hashes, pins reviewed dependency revisions where the installer permits it, and documents the remaining repository-owner trust decision.

The repository will add `REVIEW.md` as the shared cloud and local review policy. `document-for-agents` will classify, index, and check repository review policy so it changes with the rules it represents. The stale `.kilo` orchestrator command and agent will be removed.

Why: the current adapters do not complete one workflow. `plan-this` conflicts with downstream label rules, `implement-this` accepts one ticket and may bypass pull requests, and `review-this` only reports a local diff. The tracked orchestrator contradicts its retirement decision. The chosen design keeps three explicit human entry points while giving each stage one durable input, one owner, and testable state transitions.

Activation: this ADR records the approved target. Existing skill files and ADR-0009, ADR-0012, and ADR-0013 remain operative until the implementation specification closes. The implementation must then mark the replaced decisions superseded and update every affected leaf, policy, glossary entry, and derived human document in the same change.
