# 0021 — implement-this worker evidence contract

Status: accepted
Date: 2026-08-28
Discussion: https://github.com/RuralNative/RuralNative-SKILLS/issues/152

Decision: The `implement-this` seam keeps `/implement` and `/unslopify` as its only hard dependencies and does not transplant Addy Osmani's seven skills or `/build` as runtime dependencies. The new worker rules are a local contract under which a worker invokes `/implement`, not a replacement or fork of `/implement`.

Each worker reuses the acceptance criteria and smallest sufficient verification published by `plan-this`; no new required planning fields are added. The dense `Build and verify` paragraph in `SKILL.md` becomes ordered worker steps: read the dispatch packet and focused doc-cache route, classify each criterion as behavioral or one of four exempt non-behavior cases (`docs-only`, `static-content`, `rename-only`, `format-only`), run behavioral slices through RED (criterion-specific failure) → implement via `/implement` → GREEN → refactor while green, require the first behavioral criterion of a bug-fix ticket to reproduce the defect, record whitelist reasons for exempt criteria, and identify dependency/configuration criteria from the current diff so unrelated criteria remain eligible for an exemption. The worker supplies `isBugFix` and `bugFixRedConfirmed` facts rather than relying on keywords in RED prose. Version-sensitive external API changes require worker-confirmed manifest/lockfile resolution, a semver version, an authoritative documentation URL, and a supported decision. Public-interface/schema/generated-contract/numbered-invariant/cross-seam changes require worker-confirmed trigger facts plus additive/breaking/no-contract-change compatibility evidence with consumers, migration, and boundary tests plus same-change leaf/ADR updates. The worker validates and renders acceptance evidence, then runs `npm run verify` once on the final revision and commits once per verified ticket without requiring a commit per slice.

A pure evidence model (`skills/implement-this/acceptance-evidence.ts`) carries the contract: `CriterionEvidence` (behavior with non-empty `redReason`, at least one `focusedTests`, `greenPassed: true`; or non-behavior with one of four exemptions and reason; dependency/configuration criteria named by the diff-derived `dependencyOrConfigCriteria` trigger are never exempt), `ExternalSourceEvidence` and `CompatibilityEvidence` as conditional sections triggered by `touchesVersionedExternalApi` and `touchesPublicInterface` facts supplied from the current diff. Bug-fix status, first-RED confirmation, manifest/lockfile resolution, and documentation authority are worker-supplied execution facts. `validateAcceptanceEvidence` requires exactly one entry per dispatch acceptance criterion, rejects unknown or duplicate criteria, and enforces the RED and exemption rules without inferring test semantics or source authority from prose or URL syntax. `renderAcceptanceEvidence` produces one stable Markdown block with `<!-- ruralnative:acceptance-evidence:start -->` markers, escaping caller-provided `-->` consistently with `timing.ts`; it does not parse or backfill historical comments. `isDelivered` stays based on durable GitHub facts (open PR, valid closing reference, posted evidence) and does not parse historical comments. External documentation is recorded in pull-request acceptance evidence, never as mandatory source-code comments or a persistent doc-cache copy. Fresh-context and adversarial review stay in `review-this`; a failing focused test is the implementation-stage challenge.

Conflicts use the existing `document-for-agents` taxonomy: numbered-invariant collision stops before code or docs and requires an approved superseding decision; cache gap is recorded in the tracker and waits for owner approval before widening the read set; ticket ambiguity states competing ELI18 interpretations, recommends one, adds `needs-info`, and stops without a completion PR; missing test capability uses the ambiguity stop instead of manual confidence; unavailable authoritative documentation adds `needs-info` when correctness depends on it.

Why: The prior single-paragraph build stage mixed documentation, testing, setup, timing, review readiness, and final verification, hiding the red/green contract and the handling of non-behavior, versioned APIs, and public interfaces. Placing the method inline in `SKILL.md` under the existing focused route avoids a reference-file widening while making completion testable. Keeping `/implement` as the delegated method and refusing a skill transplant preserves Addy's composition model; Addy's frontend guidance targets WCAG 2.1 where W3C now recommends 2.2, and Addy's seven skills are conditional routing branches, not a uniform ticket policy.

Consequences:
- `skills/implement-this/SKILL.md` carries the ordered worker steps, taxonomy stops, and no-per-slice-commit rule while preserving the single `Issue #0` slot, `/implement`→`/unslopify` order, Task ban, worker isolation, and `npm run verify` block.
- `skills/implement-this/acceptance-evidence.ts` remains pure data-in/data-out with no network, GitHub, filesystem, clock, or Agent Manager access.
- `docs/leaves/implement-this.md` adds the evidence data flow and INV-13 (test-encoded invariant).
- `skills/implement-this/tests/` gains table-driven evidence and worker-contract composition coverage.
- `ARCHITECTURE.md` indexes this decision; `plan-this`, `review-this`, and `document-for-agents` require no behavior change.
- Existing PRs and acceptance comments remain valid; new command sessions use the new template without reprompting workers already in flight.

Activation: this decision governs new `implement-this` command sessions from today.
